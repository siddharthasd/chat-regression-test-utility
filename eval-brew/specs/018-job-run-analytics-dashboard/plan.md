# Implementation Plan: Job Run Analytics Dashboard

**Branch**: `018-job-run-analytics-dashboard` | **Date**: 2026-07-08 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/018-job-run-analytics-dashboard/spec.md`

---

## Summary

Transforms the existing Job Detail page into a full analytics report. The three-card + flat-table layout is replaced by a single scrolling view with a sticky left-hand sidebar. A new shared `RunAnalytics` engine (pure Python, no ORM) aggregates evaluation scores across all utterances in a job and produces per-parameter stat tiles (Mean, Median, Min, Max, Range, σ), a CSS histogram with ±1σ bands, and verdict distributions. A collapsible "How to read this report" guide with per-tile info-icon tooltips serves non-technical readers. Two new terminal-only export routes (long-format CSV and nested JSON) replace the existing reconstructed-input CSV route.

No new ORM models and no database migration are required. The only contract change is additive: an optional `verdict` field on existing `evaluation_scores` JSON entries. The engine is designed from the outset for reuse by feature 019 (Live Chat Analytics).

## Technical Context

**Language/Version**: Python 3.11

**Primary Dependencies**:
- FastAPI 0.115+ — existing web framework; no new routes framework needed
- SQLAlchemy 2.0 — existing ORM (read-only for analytics; no new tables)
- Jinja2 — existing server-rendered templates (no bundler)
- Bootstrap 5 (existing CDN) — sidebar layout, `data-bs-toggle="tooltip"` for info icons
- Python `statistics` stdlib — `mean()`, `median()`, `pstdev()` (no new dependency)
- Python `math` stdlib — `sqrt()` (no new dependency)
- Vanilla JS inline `<script>` — `IntersectionObserver` scrollspy, `sessionStorage` guide collapse, `window.print()`, Blob download for CSV/JSON

**Storage**: No new tables. No Alembic migration. Reads from existing `utterance` + `evaluation_result` tables via the existing `UtteranceRepository.get_by_job_ordered()` call already in the route handler.

**Testing**: pytest; in-memory SQLite fixtures (`StaticPool`); existing `conftest.py` patterns

**Target Platform**: Windows server (LAN); existing FastAPI + UvicornWorker deployment

**Project Type**: Web application — server-rendered Jinja2 templates + inline JS

**Performance Goals**:
- Detail page with analytics loads in < 3 seconds for jobs ≤ 5,000 utterances
- CSV/JSON download initiates within 2 seconds for terminal jobs ≤ 5,000 utterances

**Constraints**:
- No frontend build step — all JS inline or from existing CDN
- Analytics computation is synchronous, server-side at page load (FR-028)
- Jobs with `total_utterance_count > 5,000` skip analytics computation (FR-031)
- Histogram rendered with vanilla CSS bars only — no JS chart library (FR-017)
- Downloads available for terminal jobs only (completed / failed / cancelled) (FR-025)
- `statistics.pstdev()` (population stddev) used throughout — not sample stddev

**Scale/Scope**: 50–80 concurrent users; typical jobs < 500 utterances; 5,000-utterance guard handles edge cases

**Structure Decision**: Single existing module (`harness.ui.detail`) extended with one new pure-function module (`analytics.py`). No new packages, no new routers, no new template directories. All computation stays within the existing module boundary to minimise cross-package surface area.
