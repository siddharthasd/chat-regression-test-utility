EvalBrew — Design Documentation

Automated AI chatbot regression testing harness. Architecture, data model, API reference, and configuration guide.

EvalBrew is a Python web application that orchestrates automated regression test runs against AI chatbots and virtual assistants. Given a list of utterances, a registered connector, and a registered evaluator, it runs every test row, captures the full trace, and persists results for reporting and export.

Key concepts

Jobs

A job is one regression test run. The operator uploads a CSV of utterances, selects a connector and evaluator, then starts the job. The harness processes every row sequentially and records the full connector→contract→evaluator trace per row. All connector and evaluator configuration is snapshotted onto the job at creation and frozen once the job leaves draft status, ensuring past results are immutable.

A job finishes in one of seven states: draft, queued, running, cancelling, completed, failed, or cancelled. A single failing row never aborts the run.

Connectors and evaluators

A connector is any HTTP service that accepts a standard test request and returns a Standard Evaluation Contract. It is the bridge between the harness and the chatbot being tested. A evaluator is any HTTP service that receives the contract and returns a verdict (pass, fail, or warn) plus optional dimension scores.

Both are external services registered by URL. No harness code change is needed to add, swap, or update them. Credentials are encrypted at rest using Fernet symmetric encryption and never appear in exports or logs.

Standard Evaluation Contract

The contract is the single shared data format between the harness, connectors, and evaluators. It is defined as a JSON Schema (draft 2020-12). The connector produces it, the harness validates it, and the evaluator consumes it. The current version is "1". The contract is additive-only — new optional fields may be added without bumping the version number.

Headless API

The headless API (/api/headless/*) allows external systems such as qual-brew to drive the full evaluation lifecycle programmatically, without a browser or wizard UI. It is authenticated via Azure AD machine-to-machine Bearer tokens (Client Credentials flow). It supports job submission, real-time SSE progress streaming, result polling, and cancellation. A maximum of two concurrent in-flight headless jobs per service principal is enforced.

Live chat evaluation

In addition to batch regression jobs, the harness supports live conversational evaluation sessions (spec 017). A chat session sends individual user messages to a connector in real time, receives streaming evaluation events from the evaluator via SSE, and persists each turn with its full result. Sessions can be exported on completion.

Authentication model

Two auth models operate in parallel. Browser users authenticate via Azure AD OAuth2 Authorization Code flow (MSAL). Authorized users must be pre-registered in the user_registration table with a role of admin or user. The headless API uses M2M Bearer tokens (RS256, validated against Azure AD JWKS). Auth can be disabled for local development via HARNESS_AUTH_ENABLED=false.

Solution architecture

EvalBrew is a Python web application built on FastAPI, served by Uvicorn, and typically fronted by Nginx for TLS offload. It follows a hexagonal (ports-and-adapters) design: the harness core is completely neutral about any specific chatbot or evaluation technology. All chatbot-specific and evaluation-specific logic lives in external HTTP services (connectors and evaluators) registered by URL.

Runtime topology

Core data flow — one test row

  1. Orchestrator reads the next utterance row from the database.
  2. Connector client POSTs {testId, utteranceText, password?} to the registered connector URL.
  3. Connector validates the HTTP response and parses the Standard Evaluation Contract from the body.
  4. Contract validation (jsonschema Draft 2020-12) checks envelope shape and contractVersion.
  5. Evaluator client POSTs the full contract to the registered evaluator URL.
  6. Evaluator validates the HTTP response and parses the EvaluationResult (verdict + scores).
  7. Row result — verdict, dimension scores, full trace — is persisted to evaluation_result.
  8. Progress callbacks fire. For headless jobs, loop.call_soon_threadsafe(bus.push, ...) bridges the daemon thread into the async event loop, and an SSE progress event is emitted.
  9. Dashboard and detail views update via JS polling (browser UI) or SSE stream (headless API).
Any failure at steps 2–7 is isolated to the row. It is recorded with a stage label (connector_transport, connector_response, connector_normalization, evaluator_transport, evaluator_response, evaluator_result, etc.) and processing continues at step 1 for the next row.

Data model overview

EvalBrew's schema is managed by Alembic and comprises 10 ORM entities across two logical domains: the regression testing domain (jobs, utterances, results, registries, users) and the live chat domain (sessions, turns, turn results, evaluation events). All primary keys are UUID strings (36 characters). No ORM event listeners are used — all business rules are enforced in repository methods.

Headless Execution API

Base path: /api/headless. All endpoints require an Azure AD M2M Bearer token in the Authorization: Bearer <token> header. The token must be acquired via the OAuth2 Client Credentials flow against the harness's Azure AD app registration.

GET /api/headless/jobs/{job_id}/stream
Open an SSE stream for live per-case progress events. Replays the full event history immediately for late-connecting clients.

Response: Content-Type: text/event-stream. The stream closes automatically after the terminal event (job_complete or job_failed) is consumed. Clients that connect after the job has already finished receive the full replayed history and then an immediate close.

SSE event types

Event typePayloadDescription
job_started{}Emitted once when the job transitions from queued to running.
progress{cases_completed: N, cases_failed: N}Emitted after each test case completes. Both counts are cumulative totals.
job_complete{results_url, summary: {total, passed, failed, top_failures[]}}Terminal event. Emitted once when all rows finish. top_failures lists the first 5 failed cases with their ID and input message.
job_failed{error: "...", summary: {...}}Terminal event. Emitted when the job itself fails (not a row-level failure — a fatal error such as DB unavailability).
Thread-to-async bridging: the orchestrator engine runs in synchronous daemon threads. Progress callbacks use loop.call_soon_threadsafe(bus.push, event) to push events from the engine thread into the asyncio event loop that owns the SSE response.
GET /api/headless/jobs/{job_id}/result
Polling fallback. Returns current job status and, once terminal, the full summary.

Response: HeadlessJobResult — {job_id, status, results_url?, summary?}. The summary field is null while the job is in a non-terminal state. results_url points to the harness results export or detail page. Performance target: response within 5 seconds of job completion.

Deployment

Recommended production setup

The application runs as a Docker container on Azure Kubernetes Service (AKS), backed by Azure PostgreSQL Flexible Server (PaaS).

Start command (within the container):

uvicorn harness.ui:create_app --factory --host 0.0.0.0 --port 8000

Nginx handles TLS termination and proxies to Uvicorn on localhost. Static files can be served directly by Nginx for efficiency. The Fernet master key should be supplied via HARNESS_MASTER_KEY as a container environment variable or Kubernetes secret — no key file management is needed in this mode.

Bootstrap — first admin user

Before the web UI is accessible, the first admin must be registered via the CLI:

harness users add --email admin@example.com --role admin

Other CLI commands:

  • harness users list — list all registered users
  • harness users remove — remove a registration
  • harness users set-role — change a user's role
  • harness mock-connector — start a reference connector for dev/testing
  • harness mock-evaluator — start a reference evaluator for dev/testing
  • harness serve — start the web server directly

M2M token acquisition (headless API callers)

External systems integrating with the headless API must acquire a Bearer token using the OAuth2 Client Credentials flow before calling any /api/headless/* endpoint.

Security notes

  • Credential encryption: All auth_descriptor credential subfields (credential, password, clientSecret) are Fernet-encrypted before being written to the database. The master key must be present across redeployments. If the key changes, all stored credentials become unreadable.
  • Per-row passwords: CSV per-row passwords are never persisted. They are held in-memory in a per-job password store and evicted immediately after the connector call returns.
  • Security headers: A SecurityHeadersMiddleware is attached to the FastAPI app and injects standard security response headers on every response. Header names and values are fixed and must not be modified.
  • Session cookie: The browser session cookie is signed (Starlette SessionMiddleware). The https_only flag is true by default and must not be disabled in production.
  • Auth bypass: HARNESS_AUTH_ENABLED=false must never be set in production. It is intended for local development only.
