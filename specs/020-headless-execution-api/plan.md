# Implementation Plan: Headless Execution API

**Branch**: `020-headless-execution-api` | **Date**: 2026-07-12 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/020-headless-execution-api/spec.md`

---

## Summary

Adds a programmatic headless API to eval-brew at prefix `/api/headless`, enabling external systems (initially qual-brew) to discover connectors and evaluators, submit test cases as JSON, execute evaluation jobs, stream real-time progress via SSE, cancel in-flight jobs, and retrieve results — all authenticated via Azure AD JWT Bearer tokens rather than the existing session-cookie mechanism.

Five changes touch the existing codebase: (1) a new Alembic migration adds `submission_source`, `source_system`, `product_name`, and `feature_name` columns to the `job` table; (2) the execution engine gains an optional per-row progress-callback hook without breaking the existing code path; (3) a new per-job SSE event bus is introduced, mirroring the existing `chat/event_bus.py` pattern; (4) a new `src/harness/ui/api/` FastAPI router package is registered in `create_app()`; (5) the dashboard row view is updated to surface source metadata and submission mode for API-submitted jobs.

No new ORM tables are introduced. The migration is non-destructive: `submission_source` defaults to `'wizard'` on all existing rows.

## Technical Context

**Language/Version**: Python 3.11

**Primary Dependencies**:
- FastAPI 0.115+ — existing web framework; new `APIRouter` with prefix `/api/headless`
- SQLAlchemy 2.0 — existing ORM; one Alembic migration for the `job` table
- Alembic — existing migration framework
- MSAL Python SDK — existing; Azure AD tenant and client IDs reused for JWT audience validation
- PyJWT + cryptography — **new**; validates Azure AD Bearer tokens against the tenant's JWKS endpoint
- Pydantic v2 — existing; new request/response schemas for all headless endpoints
- pytest — existing; `TestClient` + `app.dependency_overrides` for route-level tests

**Storage**: PostgreSQL (production) / SQLite (test). One Alembic migration; no new tables.

**Testing**: pytest; in-memory SQLite `StaticPool`; existing `conftest.py` savepoint-isolation pattern; FastAPI `TestClient` with `app.dependency_overrides` to stub the Bearer auth dependency.

**Target Platform**: Windows server (LAN); existing Gunicorn + UvicornWorker deployment. No new process or service.

**Project Type**: Web application — new JSON/SSE API endpoints on the existing FastAPI app.

**Performance Goals**:
- First SSE `progress` event within 10 seconds of a 50-case job submission
- Result re-fetch endpoint responds within 5 seconds of job completion
- Validation rejections (case count, empty fields, duplicates, invalid IDs) respond within 2 seconds

**Constraints**:
- Bearer JWT auth is new; existing session-cookie auth is unchanged for all non-headless routes
- The execution engine runs on sync daemon threads; progress events must cross from the engine thread into the asyncio event loop via `loop.call_soon_threadsafe()`
- SSE stream must replay the terminal event immediately for clients that connect after the job has already completed or been cancelled
- `submission_source` defaults to `'wizard'` for all existing rows — migration is non-destructive
- Per-user in-flight limit (2 non-terminal headless jobs) is enforced via a DB count query at submission time; no in-memory counter

**Scale/Scope**: 50–80 concurrent users; max 2 headless jobs per user in non-terminal state; max 100 test cases per submission; existing `BoundedSemaphore(MAX_CONCURRENT_JOBS=4)` governs total concurrent execution across all job types.

**Structure Decision**: All new headless API code lives in `src/harness/ui/api/` to mirror the existing router-per-feature package layout. The event bus lives inside `ui/api/` (not `chat/`) because it is job-scoped, not chat-turn-scoped. The engine change is purely additive — `progress_callback` is optional and defaults to `None`, so all existing call sites are unaffected.
