# Feature Specification: Job Execution Engine (Module 10)

**Feature Branch**: `012-job-execution-engine`

**Created**: 2026-05-29

**Last Amended**: 2026-05-29

**Status**: Draft

**Input**: User description: "Module 10 — Job Execution Engine. Picks up queued jobs and runs the per-row pipeline end-to-end: instantiate connector + evaluator using snapshotted config; for each Utterance in `rowIndex` order, call `sendUtterance` → `normalize` → `evaluate` → persist EvaluationResult; catch and isolate per-row failures; update counters; on completion set `completedAt` and transition status to terminal. Runs asynchronously (start API returns immediately). Multiple jobs run concurrently with independent connector + evaluator instances per job. Fatal pre-row errors mark the Job `failed`."

> **Parent context**: This module is **the orchestrator** — the loop that turns a queued Job into a persisted set of EvaluationResults. The spec's formal module title is "Job Execution Engine"; **the body noun is "orchestrator"** for consistency with how every other spec refers to it. (The terms are interchangeable, but this spec uses "orchestrator" by default.) Per the architectural decision recorded on 2026-05-29, connectors and evaluators are no longer in-process plugins — they are **remote HTTP services** registered through CRUD modules (`013`, `014`) and called over the wire protocols defined in `007` and `008`. The orchestrator is correspondingly thinner: there is no `connect`/`disconnect` lifecycle, no in-process `normalize` step (the connector service returns a pre-normalized Standard Evaluation Contract instance per `007 FR-003`), and no per-job stateful handle. Each row is two independent HTTP requests: one to the connector service (returns a contract) and one to the evaluator service (returns an EvaluationResult). The orchestrator consumes the snapshotted endpoint configuration from `009 FR-001` / `FR-005` (via parent `FR-023`), the wire protocols + generic HTTP client from `007` / `008`, the at-rest credential decryption utility (parent `FR-023a` / `007 FR-013`–`FR-017`), the in-memory password store from `011 FR-015`, the per-row EvaluationResult shape from `009 FR-003`, and the cancellation rules from parent `FR-024` (with stub creation per `009 FR-003a`). It is the runtime enforcement point for parent `FR-016`/`FR-017` (per-row failure isolation), `FR-025` (no retries at orchestrator layer), `FR-022` (orphan reconciliation), and the partial-completion semantics. Parent-spec premises apply: single-user, single-process, no auth. The Module 10 input's mention of `CompletedWithErrors` as a terminal state was dropped by precedent — terminal status is always `completed` regardless of `failedCount`, with the "Completed with errors" rendering being a UI label per `004` (per `009 Q2`). The user's "Module 10" maps to our `012-` directory by the convention used for prior modules.

## Clarifications

### Session 2026-05-29

- Q: Parent `FR-022` requires orphaned `running` jobs (left over from a crash/restart) to be reconciled to a deterministic terminal or paused state. The current canonical enum has no `paused`. How should the engine reconcile them? → A: **Transition to `failed`.** The engine, at process startup, scans the database for any Job whose persisted `status == running` (or `cancelling`), and atomically transitions each to `failed` with an explanatory `errorDetails` value (e.g., `"harness restarted while job was running"`) on the Job. No new lifecycle state is introduced; no parent enum amendment is needed. Recovery path: tester creates a new Job and re-uploads the CSV (per parent `FR-010a`'s "tester-visible state requires explicit re-upload"). The in-memory password store entries for the orphaned job — if any — are cleared as part of reconciliation.

### Session 2026-05-29 (Reshape)

- Q: Now that connectors and evaluators are remote HTTP services, what does the per-row pipeline look like? → A: **Two HTTP calls per row, in sequence:** (1) `POST` to the snapshotted connector endpoint with `{testId, utteranceText, password?}` per `007 FR-002`; the response body is a Standard Evaluation Contract instance per `007 FR-003`. The harness re-validates the contract against the bundled schema as a sanity check. (2) `POST` to the snapshotted evaluator endpoint with the contract instance as the body per `008 FR-002`; the response body is an EvaluationResult per `008 FR-003`. The harness validates the EvaluationResult per `008 FR-005b`. The pipeline drops the previously-required in-process `normalize` step entirely (the connector service is responsible for normalization). The pipeline drops `connect`/`disconnect` entirely (each row is two stateless HTTP requests).
- Q: What error stages replace the previous three-stage taxonomy (`connector`, `normalization`, `evaluation`)? → A: **A finer-grained set** that distinguishes transport from response from content validation, separately for connector and evaluator:
  - `connector_transport` — DNS / connection refused / TLS handshake / harness-side timeout exceeded for the connector call.
  - `connector_response` — connector returned non-2xx HTTP status.
  - `connector_normalization` — connector returned 2xx with invalid JSON or a body that fails Standard Evaluation Contract validation.
  - `connector_auth` — decryption of the stored connector credential failed (key missing/wrong).
  - `evaluator_transport` / `evaluator_response` / `evaluator_result` / `evaluator_auth` — symmetric, on the evaluator side.
  - `password_lookup` — the per-row password was absent from the in-memory store at dispatch time.
  
  These values constitute the v1 `errorStage` enum referenced by `006 FR-009` (extended), `009 FR-003`, `007 FR-006`, and `008 FR-006a`. Earlier specs that referred to stages `connector`, `normalization`, `evaluation` are interpreted as referring to the prefix-matching groups in this finer taxonomy.
- Q: What is the pre-row failure model now that there is no `connect()` call to fail? → A: **There is no pre-row instantiation step** in the new model. The only true pre-row failure is "the in-memory password store is empty for this Job's `jobId`" — i.e., the password store didn't survive a harness restart between upload and execution (per parent `FR-010a`). All other failure modes that were "pre-row" in the old design (missing registry entry, decryption failure, unreachable endpoint) now manifest **per-row** as `connector_*` or `evaluator_*` errors and the Job's terminal status remains `completed` with high `failedCount`, not `failed`. The exception is `connector_auth` / `evaluator_auth` (credential decryption failure) — if the decryption fails for the FIRST row, every subsequent row will fail the same way, but each row still gets its own EvaluationResult; the Job still ends `completed`. (Future work MAY add a fast-fail heuristic: e.g., if the first K rows all fail with the same `auth` error, give up early. Out of scope for v1.)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Execute a queued job end-to-end through the pipeline (Priority: P1)

The wizard's "Start Job" click (per `003 FR-016` + the gate in `001 FR-027`) atomically transitions a Job from `draft` to `queued` and emits an enqueue signal. The orchestrator, running asynchronously in the harness process, picks up the queued Job, transitions it to `running`, resolves the snapshotted connector endpoint (URL, auth descriptor, timeout, expects-per-row-password flag) and evaluator endpoint (URL, auth descriptor, timeout, declared scoring dimensions) from the Job's snapshot (per parent `FR-023` / `009`), and iterates the Job's persisted Utterance rows in `rowIndex` order. For each row, it looks up the password from the in-memory store (per `011 FR-015`), `POST`s to the connector endpoint to receive a normalized Standard Evaluation Contract instance, `POST`s to the evaluator endpoint to receive an EvaluationResult, validates both, applies harness-derived annotations (`harnessAnnotations` per `008 FR-005a`), and persists a complete EvaluationResult atomically with `processedCount` and (if applicable) `failedCount` updates. Per-row password is evicted from the store immediately after the connector call completes. After the last row, the orchestrator sets `completedAt`, transitions status to `completed`, and clears any remaining password store entries for the Job.

**Why this priority**: This is the entire purpose of Module 10. Without it, every preceding spec is just plumbing with no payload. It is the MVP slice.

**Independent Test**: With a Job in `queued` status carrying 5 Utterance rows + matching in-memory password store entries, a snapshotted bundled-mock-connector registration (`007 FR-018`–`FR-022`), and a snapshotted bundled-mock-evaluator registration (`008 FR-022`–`FR-027`), trigger the orchestrator. Verify: (a) 5 HTTP `POST`s issued to the connector endpoint in `rowIndex` order with correct per-row body; (b) each connector response is contract-conformant; (c) 5 HTTP `POST`s issued to the evaluator endpoint in `rowIndex` order with the contract instance as body; (d) each evaluator response is a well-formed EvaluationResult; (e) 5 EvaluationResult records persisted with `errorStatus == null` and `evaluationVerdict` populated; (f) Job ends with `processedCount == 5`, `failedCount == 0`, `completedAt` set, `status == completed`; (g) the in-memory password store contains zero entries for that Job at completion.

**Acceptance Scenarios**:

1. **Given** a Job in `queued` status with N Utterance rows, a snapshotted connector and evaluator endpoint config, and N matching entries in the in-memory password store, **When** the orchestrator picks up the Job, **Then** the Job transitions `queued → running`, `startedAt` is recorded (if not already set by the wizard), and the orchestration loop begins.
2. **Given** the orchestrator is processing row K, **When** it looks up the row's password, **Then** the lookup retrieves the entry from the in-memory store keyed by `(jobId, utteranceId)`; if the snapshotted connector registration's `expectsPerRowPassword` is `true`, the password is forwarded in the connector HTTP body as `"password"`; if `false`, the `"password"` field is omitted from the body entirely. The store entry is removed immediately after the connector HTTP call returns (success or failure).
3. **Given** every row of an N-row Job completes successfully, **When** the orchestrator finishes the loop, **Then** the Job's `processedCount == N`, `failedCount == 0`, `completedAt` is set, `status == completed`.
4. **Given** the Job completes (any terminal status), **When** the orchestrator wraps up, **Then** the in-memory password store contains zero entries keyed by that Job's `jobId`.

### User Story 2 - Isolate per-row failures; the job continues (Priority: P1)

A row's connector call times out, or returns a non-2xx, or returns a body that fails contract validation. Or the evaluator call fails analogously. The orchestrator catches the failure category, persists an EvaluationResult for that row with `errorStatus = "failed"` and `errorStage` set to the specific stage (per the 2026-05-29 reshape clarification's finer taxonomy); increments the Job's `failedCount`; and proceeds to the next row. No HTTP connection is held across rows, so there is no handle teardown to worry about. The Job continues even if every row fails — the terminal status is still `completed` (with `failedCount == totalUtteranceCount`), not `failed`.

**Why this priority**: This is the "regression-test-tool resilience" property. Without it, one flaky row torpedoes the whole run. Equal-priority with US1 because both are required for the orchestrator to deliver value.

**Independent Test**: With a job whose Utterance rows include some that the bundled mock connector / evaluator is instrumented to fail in different ways — row 2's connector times out, row 3's connector returns a contract-non-conformant body, row 4's evaluator returns malformed JSON — verify: (a) 5 EvaluationResults are persisted (one per row), (b) row 2 has `errorStage = "connector_transport"`, row 3 has `errorStage = "connector_normalization"`, row 4 has `errorStage = "evaluator_result"`, each with `errorDetails` carrying the cause, (c) rows 1 and 5 have `errorStatus = null` and complete evaluation data, (d) `processedCount == 5`, `failedCount == 3`, `completedAt` set, `status == completed`.

**Acceptance Scenarios**:

1. **Given** a row whose connector HTTP call fails at the transport layer (DNS / refused / TLS / harness-side timeout), **When** the orchestrator catches it, **Then** an EvaluationResult is persisted for that row with `errorStatus = "failed"`, `errorStage = "connector_transport"`, `errorDetails` carrying the cause, and the Job's `failedCount` is incremented atomically.
2. **Given** a row whose connector returns a non-2xx HTTP status, **When** the orchestrator inspects the response, **Then** an EvaluationResult is persisted with `errorStatus = "failed"`, `errorStage = "connector_response"`, `errorDetails` carrying the status code and a truncated body preview.
3. **Given** a row whose connector returns 2xx with a body that fails Standard Evaluation Contract validation (per `006 FR-008`), **When** the orchestrator detects the violation, **Then** an EvaluationResult is persisted with `errorStatus = "failed"`, `errorStage = "connector_normalization"`, `errorDetails` carrying the per-field violation list (per `006 FR-009`).
4. **Given** a row whose evaluator HTTP call fails at any of the four evaluator stages (`evaluator_transport` / `evaluator_response` / `evaluator_result` / `evaluator_auth`), **When** the orchestrator detects the failure per `008 FR-006a`, **Then** an EvaluationResult is persisted with the corresponding stage and details; `failedCount` is incremented.
5. **Given** any per-row failure, **When** the orchestrator handles it, **Then** the next row is processed; the in-memory password store entry for the failed row is still evicted (if the eviction point — immediately after the connector call returns — was reached).
6. **Given** a Job where EVERY row fails, **When** the orchestrator completes the loop, **Then** the Job's `processedCount == totalUtteranceCount`, `failedCount == totalUtteranceCount`, terminal status `completed` (NOT `failed`); the dashboard / detail view render this as "Completed with errors" per `004 FR-005`.

### User Story 3 - Honor the soft-cancel sequence mid-run (Priority: P2)

The tester clicks Cancel on a `running` Job from the Job Detail View (per `004 FR-018`). The orchestrator detects the cancel signal, allows the currently-in-flight row's connector+evaluator pipeline to run to natural completion or failure (per parent `FR-024`), then stops invoking further rows. Remaining queued Utterances get EvaluationResult stubs created by the data layer (per `009 FR-003a`) with `errorStatus = "cancelled"`. The orchestrator transitions the Job from `cancelling → cancelled`, sets `completedAt`, and clears the in-memory password store for the Job. (There is no `disconnect()` to call.)

**Why this priority**: Cancel is the primary UX escape hatch for runaway jobs. Equal-priority with US4/US5 because cancellation, restart-recovery, and concurrency are all P2 robustness layers on top of the P1 happy/per-row-fail paths.

**Independent Test**: Start a job with 10 rows against an instrumented mock connector that sleeps for several seconds per request. Mid-run, after row 4 starts but before row 5, trigger Cancel. Verify: (a) row 4 finishes naturally and gets a normal EvaluationResult (not cancelled); (b) rows 5–10 get cancellation-stub EvaluationResults (per `009 FR-003a`); (c) Job's `processedCount` counts rows 1–4 (per `009 FR-001`'s definition that excludes `cancelled`); (d) `failedCount == 0` if rows 1–4 succeeded; (e) Job transitions through `running → cancelling → cancelled` atomically with the stub creation; (f) the in-memory password store is empty for the Job after cancellation.

**Acceptance Scenarios**:

1. **Given** a `running` Job whose tester has clicked Cancel, **When** the orchestrator receives the signal, **Then** the orchestrator transitions the Job's status to `cancelling`; the in-flight row's pipeline runs to natural completion (success or failure) and its EvaluationResult is persisted normally.
2. **Given** the in-flight row has completed (the Job is in `cancelling`), **When** the orchestrator considers the next row, **Then** the orchestrator STOPS — no further HTTP calls are made; the data layer's atomic `cancelling → cancelled` transition creates EvaluationResult stubs for every remaining Utterance (per `009 FR-003a`).
3. **Given** the cancellation completes, **When** the orchestrator wraps up, **Then** `completedAt` is set, status is `cancelled`, and the in-memory password store contains zero entries for the Job.
4. **Given** a Cancel signal arrives AFTER the orchestrator has already begun the `running → completed` transition (race), **When** the data layer applies updates, **Then** the cancel is refused (the Job is already terminal) and the tester is shown an actionable message per `004 FR-018`'s race-edge case.

### User Story 4 - Reconcile orphaned `running` / `cancelling` jobs at process startup (Priority: P2)

A previous harness run crashed or was killed mid-job. On restart, the database holds at least one Job in `running` or `cancelling` status whose orchestrator process no longer exists. The orchestrator, before doing any other work, scans for such jobs and atomically marks each `failed` with an explanatory `errorDetails`. The in-memory password store for those orphaned jobs is empty (it didn't survive the restart per `011 FR-015`'s process-exit-clear rule); per parent `FR-010a`, recovery requires the tester to re-upload the CSV against a new Job.

**Why this priority**: Without reconciliation, every crashed harness leaves a "stuck running" Job in the database that the dashboard shows confusingly forever. Equal-priority with US3/US5.

**Independent Test**: Manually set a Job's persisted status to `running` (simulating a crash mid-job). Boot the harness. Verify: (a) within 5 seconds of startup, the Job's status transitions to `failed` with `errorDetails` carrying a clear orphan-recovery message; (b) the Job's `completedAt` is set; (c) the in-memory password store contains zero entries for that Job; (d) the dashboard shows the Job as `failed` (per `002 FR-004`); (e) the tester can create a new Job and re-upload the CSV to retry.

**Acceptance Scenarios**:

1. **Given** the harness process starts, **When** the orchestrator performs its orphan-reconciliation pass, **Then** it queries the data layer for every Job whose `status` is `running` or `cancelling`, and atomically transitions each to `failed` with `errorDetails` set to a clear orphan-recovery message (e.g., `"harness restarted while job was running; create a new job to retry"`) and `completedAt` set to the current moment.
2. **Given** the orphan reconciliation has completed, **When** any other module reads or writes persistent state, **Then** no Job is in `running` or `cancelling` status — they have all been reconciled. This matches parent `SC-008`'s "no job remains in `running` after restart within 5 seconds."
3. **Given** an orphaned Job had EvaluationResult stubs created mid-run, **When** the orphan reconciliation runs, **Then** any existing EvaluationResults are preserved as-is (they reflect rows that did execute before the crash); only the Job's status changes. No retroactive stub creation runs.

### User Story 5 - Run multiple jobs concurrently without interference (Priority: P2)

The tester starts Job A; the orchestrator begins processing. Before A finishes, the tester starts Job B. The orchestrator picks up B and runs it concurrently. Each Job has its own per-row HTTP request stream and its own in-memory password store entries (keyed by `(jobId, utteranceId)`). Each Job's `processedCount` / `failedCount` / `status` updates independently. Per `007 FR-005` and `008 FR-021`, rows within each Job are serialized — but two Jobs' rows can be in flight simultaneously.

**Why this priority**: Comparative testing — running two configurations side by side against the same CSV — is the harness's headline use case (per parent User Story 3). Without concurrent execution, the harness becomes a one-at-a-time bottleneck.

**Independent Test**: Start two Jobs simultaneously (or as close as possible). Verify: (a) both have `status == running` at the same time, (b) each has independent EvaluationResults accumulating, (c) each has its own `processedCount` ticking up independently, (d) cancelling one Job does not affect the other, (e) terminal status of one Job is reached without waiting for the other.

**Acceptance Scenarios**:

1. **Given** two Jobs both in `queued` status when the orchestrator boots (or are enqueued in close succession), **When** the orchestrator picks them up, **Then** each Job dispatches its own HTTP request stream independently; no shared state at the harness layer.
2. **Given** two concurrent running Jobs use the same registered connector (e.g., both snapshotted the same connector registration), **When** they execute concurrently, **Then** each issues its own independent HTTP requests; the connector service handles concurrent inbound requests itself.
3. **Given** two concurrent running Jobs, **When** one is cancelled, **Then** the other continues unaffected; the in-memory password store entries for the cancelled Job are cleared independently of the other Job's entries.
4. **Given** two concurrent running Jobs A and B, **When** Job A's status updates (e.g., to `cancelling`), **Then** Job B's status is unchanged.

### User Story 6 - Fail the Job cleanly when the in-memory password store is empty (Priority: P3)

The orchestrator picks up a `queued` Job, attempts to dispatch the first row, and finds the in-memory password store empty for the Job's `jobId` (e.g., the harness restarted between CSV upload and Start, per parent `FR-010a`). Because no further work is possible without per-row credentials (when the snapshotted connector's `expectsPerRowPassword` is true; if it's false, the missing store is fine and execution proceeds normally), the orchestrator transitions the Job to `failed` with `errorDetails` naming the cause, sets `completedAt`, and DOES NOT invoke any per-row pipeline.

**Why this priority**: This is the lone true pre-row failure in the new model. All other "pre-row" failure modes from the old design (missing registry entry, decryption failure, `connect()` raise) now manifest per-row in the new finer error taxonomy and result in `completed` Jobs with high `failedCount`, not pre-row `failed` Jobs. P3 because it is rare and well-isolated.

**Independent Test**: Create a Job whose snapshotted connector has `expectsPerRowPassword = true`. Manually clear the in-memory password store for that Job's `jobId`. Trigger the orchestrator. Verify: (a) the Job's terminal status is `failed`, (b) `errorDetails` names the empty-store cause, (c) `completedAt` is set, (d) no EvaluationResult rows exist for that Job's Utterances (no pipeline was invoked).

**Acceptance Scenarios**:

1. **Given** a `queued` Job whose snapshotted connector requires per-row passwords AND the in-memory password store is empty for this `jobId`, **When** the orchestrator attempts to dispatch the first row, **Then** the Job transitions to `failed` with `errorDetails` carrying the "credentials no longer in memory — re-upload CSV via a new Job" message per parent `FR-010a`; no HTTP calls are issued.
2. **Given** a `queued` Job whose snapshotted connector does NOT require per-row passwords AND the in-memory store is therefore not expected to have entries, **When** the orchestrator dispatches the first row, **Then** dispatch proceeds normally; the connector HTTP body omits the `password` field per `007 FR-002`.
3. **Given** the orchestrator detects the empty-store condition for a job needing passwords, **When** it transitions the Job to `failed`, **Then** no EvaluationResults are created for that Job's Utterances (the failure occurred before any row was attempted).

### Edge Cases

- A Job has zero Utterance rows (impossible via Module 8's validation per `011 FR-009`'s "no data rows" rejection, but defensive). The orchestrator skips the row loop entirely and transitions to `completed` with `processedCount == 0`, `failedCount == 0`.
- The orchestrator is processing row N when the harness gets a SIGTERM. The in-flight row's pipeline completes if possible (single HTTP request is naturally short); otherwise the Job is left in `running` and gets reconciled to `failed` on next startup per US4.
- A Cancel arrives DURING the orchestrator's startup orphan-reconciliation pass (impossible in practice — startup runs before any tester action — but defensive). The orphan pass overrides; the Job ends in `failed`.
- Concurrent jobs target the same connector or evaluator endpoint. Each issues independent HTTP requests; the remote service is responsible for handling concurrent inbound load.
- The connector or evaluator service hangs without responding. The orchestrator enforces the snapshotted `timeoutSeconds` per `007 FR-004` / `008 FR-006`; the call is aborted locally and recorded as `*_transport` with a `"timeout exceeded"` detail. No harness-layer retry (per parent `FR-025`).
- The connector returns a contract whose `contractVersion` field doesn't match the bundled schema's accepted range. Per `006 FR-015`, the contract instance is rejected at validation time with `errorStage = "connector_normalization"`. Per the 2026-05-29 reshape (`001 FR-020`, `003 FR-013` reserved, `006 FR-012` reserved), contract-version compatibility is **strictly a runtime concern** in v1 — the wizard-time gate was deprecated when evaluator registrations stopped carrying a contract-version field; this rejection IS the canonical mechanism, not defense-in-depth.
- The data layer write fails mid-row (e.g., disk full while persisting the EvaluationResult). The orchestrator catches the failure, marks the row `failed` with a "persistence error" detail (best-effort), and proceeds to the next row. Subsequent rows likely fail with the same cause; eventually the Job reaches terminal `completed` with all rows `failed`. The harness operator must resolve the disk issue out-of-band.
- The snapshotted connector or evaluator's stored credential cannot be decrypted at HTTP-call time (key rotated / missing). The row records `errorStage = "connector_auth"` or `"evaluator_auth"` per `007 FR-016` / `008 FR-016`; subsequent rows likely fail the same way; the Job ends `completed` with high `failedCount`. (See Reshape clarification's "no fast-fail in v1" note.)
- The orchestrator's snapshotted connector or evaluator registration has since been archived (soft-deleted). Per `007 FR-012`–`FR-013` and `008 FR-012`–`FR-013`, the orchestrator dispatches normally using the Job snapshot; archival affects only the wizard's selectability, not historical execution.
- The orchestrator's snapshotted connector or evaluator registration has since been hard-deleted. Per `013 FR-019` / `014 FR-024`, hard delete is blocked when historical jobs reference the registration, so this case is structurally prevented. (Defense-in-depth: if it somehow happens, the snapshot itself contains endpoint + auth + timeout, so dispatch still works.)
- A new job is enqueued while the orchestrator is at its concurrency limit (plan-level cap). The job stays in `queued` until a slot frees. The dashboard shows `queued` per `002 FR-004`. Plan-level: when slots free, FIFO or some other ordering.
- A row's connector call returns successfully and an EvaluationResult is being constructed; the harness crashes before persisting. On orphan reconciliation, the Job goes to `failed`; the unsaved row is lost (no EvaluationResult; the tester re-uploads CSV in a new Job to retry).

## Requirements *(mandatory)*

### Functional Requirements

#### Engine lifecycle and job pickup

- **FR-001**: The orchestrator MUST run **asynchronously** with respect to the request that enqueued a Job. The wizard's `start` action (per `003 FR-016`'s atomic `draft → queued` transition) MUST return as soon as the Job's status is `queued` and the enqueue signal has been emitted; the orchestrator then picks up the Job in the background. No tester-facing call blocks waiting for Job completion.
- **FR-002**: At process startup, BEFORE any other module reads or writes persistent state, the orchestrator MUST perform an **orphan-reconciliation pass** over the data layer: scan every Job whose persisted `status` is `running` or `cancelling`, atomically transition each to `failed` with `errorDetails` set to a clear orphan-recovery message (e.g., `"harness restarted while job was running"` or `"harness restarted while job was cancelling"`) and `completedAt` set to the current moment. The in-memory password store contains no entries from prior process lifetimes (per `011 FR-015`'s process-exit-clear rule); the orchestrator MUST NOT attempt to restore them. The orphan-reconciliation pass MUST complete within 5 seconds of startup (mirrors parent `SC-008`). **Interaction with cancellation-stub discipline (`009 FR-003a`):** for a Job orphaned in `cancelling` status, the orphan pass MUST NOT create the cancellation stubs that `009 FR-003a` writes during the normal `cancelling → cancelled` sequence — the Job is going to `failed`, not `cancelled`, so the stub-creation rule does not fire. Any partial EvaluationResults already persisted by the in-flight row (or by an earlier `cancelling`-time stub-write that didn't finish) are preserved as-is per US4 Acceptance Scenario 3 ("any existing EvaluationResults are preserved as-is ... only the Job's status changes"). The net effect: a `cancelling`-when-crashed Job ends `failed` with whatever EvaluationResults the prior process committed before dying; rows that were neither processed nor stubbed are simply absent (the Job's `processedCount` will be less than `totalUtteranceCount`, mirroring any other `failed` Job).
- **FR-003**: After orphan reconciliation, the orchestrator MUST pick up Jobs whose status is `queued` and begin processing them. The orchestrator MAY process multiple Jobs concurrently (per parent `FR-011`, this spec's US5). Per-job processing MUST be initiated by a status transition `queued → running` and the recording of `startedAt` (if not already set).
- **FR-004**: When the orchestrator picks up a Job, it MUST read the Job's snapshotted configuration from the data layer (per `009 FR-001`). The relevant snapshot fields are: `connectorId`, `connectorName`, `connectorEndpointUrl`, `connectorAuthDescriptor`, `connectorTimeoutSeconds`, `connectorExpectsPerRowPassword`, `evaluationAgentId`, `evaluationAgentName`, `evaluatorEndpointUrl`, `evaluatorAuthDescriptor`, `evaluatorTimeoutSeconds`, `evaluatorDeclaredScoringDimensions`. The orchestrator MUST NOT consult the current state of the Connector Registry or Evaluator Registry — the Job's snapshot is the sole source of truth (per parent `FR-023`). Both `connectorName` and `evaluationAgentName` are purely display labels; the orchestrator does NOT use either for any runtime decisions. The declared scoring dimensions on the evaluator snapshot are used at result-validation time to compute `harnessAnnotations.unexpected_score_dimensions` per `008 FR-005a`.
- **FR-005**: The orchestrator MUST decrypt the snapshotted connector and evaluator credentials using the machine-local encryption utility (per parent `FR-023a` / `007 FR-013`–`FR-017`) **just-in-time** when constructing each row's HTTP request auth header. Decrypted plaintext MUST NEVER appear in any persistent surface (logs, exports, UI, database) per `007 FR-015`. Plaintext lifetime is bounded by a single HTTP request: constructed when the header is being built, discarded no later than when the HTTP response is received (or the request is aborted).

#### Snapshot resolution (no instantiation)

- **FR-006**: The orchestrator does NOT instantiate a connector or call `connect()`. There is no per-job stateful handle in the new model. The snapshotted connector configuration is used directly to construct per-row HTTP requests.
- **FR-007**: The orchestrator does NOT instantiate an evaluator or invoke an in-process `evaluate()` method. The snapshotted evaluator configuration is used directly to construct per-row HTTP requests.
- **FR-008**: *(Reserved — formerly defined `connect()` invocation; superseded by the stateless HTTP model. The FR number is preserved for stable cross-spec references; current content: no requirement, see `FR-011` for the per-row HTTP dispatch model.)*
- **FR-009**: *(Reserved — formerly defined `ConnectionHandle` reuse; superseded.)*
- **FR-010**: *(Reserved — formerly described evaluator instantiation; superseded.)*

#### Per-row pipeline

- **FR-011**: For each Utterance row of the Job (ordered by `rowIndex` per `009 FR-002`), the orchestrator MUST run the following pipeline in sequence:
  1. **Password lookup**: if the snapshotted connector's `expectsPerRowPassword` is `true`, look up the row's password from the in-memory password store keyed by `(jobId, utteranceId)` (per `011 FR-015`). If absent, halt per-row processing for this Job; transition the Job to `failed` per US6. If `expectsPerRowPassword` is `false`, no lookup is performed and the password field is omitted from the connector HTTP body.
  2. **Connector HTTP call**: construct a `POST` to the snapshotted `connectorEndpointUrl` with `Content-Type: application/json`, the auth header constructed per `007 FR-007`–`FR-007d` (decrypting the snapshotted credential just-in-time), and a body of `{"testId": "...", "utteranceText": "..."}` (with `"password": "..."` included if and only if the snapshotted `expectsPerRowPassword` is `true`). Await the response within `connectorTimeoutSeconds`; abort locally on timeout.
  3. **Password eviction**: IMMEDIATELY after the connector HTTP call returns (success or failure), the orchestrator MUST evict the row's password entry from the in-memory store (per `011 FR-015` per-row eviction). Eviction happens regardless of the call's outcome.
  4. **Contract validation**: if the connector returned 2xx, validate the response body against the bundled Standard Evaluation Contract schema (per `006 FR-008`). A failure here is recorded as `errorStage = "connector_normalization"`; the pipeline stops for this row.
  5. **Evaluator HTTP call**: if the contract validated, construct a `POST` to the snapshotted `evaluatorEndpointUrl` with `Content-Type: application/json`, the auth header constructed for the evaluator, and a body that is the contract instance JSON verbatim. Await the response within `evaluatorTimeoutSeconds`; abort locally on timeout.
  6. **EvaluationResult validation**: if the evaluator returned 2xx, validate the response body per `008 FR-005b` (required fields present, verdict in closed enum, scores entries well-shaped, timestamp valid). A failure is recorded as `errorStage = "evaluator_result"`; the pipeline stops for this row.
  7. **Harness annotation**: compute `harnessAnnotations.unexpected_score_dimensions` by comparing the evaluator's emitted `parameter_name` values to the snapshotted `evaluatorDeclaredScoringDimensions` per `008 FR-005a`.
  8. **Persist**: the orchestrator MUST persist exactly one EvaluationResult row per Utterance (per `009 FR-003`), atomically with the Job's counter updates. The EvaluationResult carries whichever stage data succeeded — `rawChatbotResponse` is null if the connector failed before returning; `normalizedContract` (the contract instance) is null if the connector returned a body that failed contract validation, otherwise it holds the validated contract; `evaluationVerdict` / `evaluationScores` / `metadata` / `harnessAnnotations` are null if evaluation failed; `errorStatus` / `errorStage` / `errorDetails` reflect the failure stage if any.
- **FR-012**: Per-row failures at ANY stage MUST be isolated: the row's EvaluationResult is persisted with `errorStatus = "failed"` and `errorStage` set to one of the values defined in the 2026-05-29 Reshape clarification (`connector_transport` / `connector_response` / `connector_normalization` / `connector_auth` / `evaluator_transport` / `evaluator_response` / `evaluator_result` / `evaluator_auth` / `password_lookup`); the Job's `failedCount` is incremented atomically with the persistence (per `009 FR-001` / `FR-020`); the next row is processed. Per-row failure MUST NOT cause the Job to abort (per parent `FR-016`, this spec's US2).
- **FR-013**: The orchestrator MUST NOT retry any failed per-row HTTP call (per parent `FR-025`). Each connector and evaluator HTTP call is single-shot. The connector or evaluator service MAY retry internally per its own design; the orchestrator does not.
- **FR-014**: The orchestrator MUST update the Job's `processedCount` atomically when persisting each row's EvaluationResult. Per `009 FR-001`, `processedCount` counts EvaluationResults where `errorStatus IN (null, "failed")` — i.e., success OR failure of an attempted row. Cancelled-before-process rows (whose stubs are created at `cancelling → cancelled` per `009 FR-003a`) are NOT counted here.
- **FR-015**: *(Reserved — formerly required `disconnect(handle)` on Job termination; superseded by the stateless HTTP model. No teardown call exists in the new model. The FR number is preserved for stable cross-spec references.)*

#### Terminal transition

- **FR-016**: When the orchestrator finishes a Job's per-row loop without cancellation or fatal pre-row failure (the only pre-row failure being US6's empty password store), it MUST atomically: (a) set `completedAt` to the current moment, (b) transition `status` to **`completed`** — regardless of whether `failedCount == 0` or `failedCount > 0` or even `failedCount == totalUtteranceCount` (per `004 FR-005`, the "Completed with errors" rendering is a UI label, NOT a stored state), (c) clear all remaining in-memory password store entries for the Job (the Job-terminal backstop per `011 FR-015`).
- **FR-017**: If the orchestrator encountered the US6 pre-row failure (empty password store for a Job requiring per-row passwords), it MUST atomically: (a) set `completedAt`, (b) transition `status` to **`failed`** with `errorDetails` naming the cause, (c) clear any in-memory password store entries (defensive, expected to be no-op since the failure was triggered by absence). No EvaluationResults are created in this pathway.
- **FR-018**: The orchestrator MUST NEVER transition a Job's stored `status` to `CompletedWithErrors` or `Configured` or any value not in the canonical lifecycle enum (parent `Job` entity per `001` Key Entities and `009 FR-001`). These are not lifecycle states; the canonical enum is `draft / queued / running / cancelling / completed / failed / cancelled` (per `009`'s 2026-05-29 status-enum clarification). UI labels derived from those states (e.g., "Completed with errors") are the consumers' responsibility.

#### Cancellation handling

- **FR-019**: When the data layer signals a Cancel for a `running` Job (the tester triggered `004 FR-018`'s Cancel control, which transitions the Job to `cancelling` per parent `FR-024`), the orchestrator MUST detect the signal at the next per-row boundary AND MUST allow the currently-in-flight row's pipeline to run to natural completion or failure. The orchestrator MUST NOT interrupt an in-flight HTTP call (it MAY honor the snapshotted `timeoutSeconds` as normal; it MUST NOT add a cancellation-induced abort).
- **FR-020**: After the in-flight row completes (its EvaluationResult is persisted normally), the orchestrator MUST stop dispatching further rows for that Job. It MUST coordinate with the data layer to atomically (a) create EvaluationResult stubs for all remaining Utterances with `errorStatus = "cancelled"` per `009 FR-003a`, (b) transition the Job from `cancelling` to terminal `cancelled`, (c) set `completedAt`, (d) clear the in-memory password store for the Job.
- **FR-021**: A Cancel signal that arrives AFTER the orchestrator has already begun the `running → completed` transition (race) MUST be refused by the data layer (per `004 FR-018`'s race-edge case); the orchestrator MUST NOT receive or act on such a refused signal.

#### Concurrent execution

- **FR-022**: The orchestrator MUST support multiple Jobs running concurrently without interference (per parent `FR-011`, US5). Each concurrent Job MUST have its own per-row dispatch context (independent HTTP requests, independent counter updates, independent in-memory password store entries). Independence is structural: the store is keyed by `(jobId, utteranceId)`; HTTP requests carry no implicit shared state at the orchestrator layer.
- **FR-023**: Within a single Job, the orchestrator MUST serialize per-row dispatches (per `007 FR-005` and `008 FR-021`). No two rows of the same Job are in flight simultaneously in v1. Cross-job parallelism is unconstrained at the orchestrator layer except by plan-level concurrency limits.
- **FR-024**: Cancellation or terminal transition of one concurrent Job MUST NOT affect another concurrent Job's state — counters, password store entries, and lifecycle status all remain isolated per `(jobId)`.

### Key Entities *(include if feature involves data)*

- **Job Execution Worker** *(in-process, plan-level shape)*: The async unit of work that owns one Job's runtime — its per-row dispatch loop, its counter updates, its association with the in-memory password store. One worker per concurrent Job. Lives for the duration of the Job; ends when the Job reaches terminal status. Concrete implementation (asyncio task, threading.Thread, separate worker process, etc.) is plan-level.
- **Per-row Pipeline State** *(transient, per-row, in-memory)*: The intermediate state of one row's pipeline: the password (briefly), the connector HTTP response (briefly), the parsed contract instance (briefly), the evaluator HTTP response (briefly), the parsed EvaluationResult. Lives only for the duration of one row's processing; discarded after the row's EvaluationResult is persisted. Notably: the password is evicted from the in-memory store IMMEDIATELY after the connector HTTP call returns, not at end-of-row.
- **Orphan Reconciliation Pass** *(transient, startup)*: A one-shot operation at orchestrator boot that walks the data layer for Jobs in `running` / `cancelling` status, transitions them to `failed`, and clears any stale in-memory state (there isn't any in practice, since the store is process-scoped). Completes within 5 seconds of startup.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A `queued` Job with N Utterance rows + matching password store entries + valid snapshotted endpoints completes successfully: status reaches `completed`, `processedCount == N`, `failedCount == 0`, `completedAt` set, exactly N connector HTTP `POST`s and N evaluator HTTP `POST`s issued in `rowIndex` order, in-memory password store empty for the Job. Verifiable by automated end-to-end test against the bundled mock connector + mock evaluator.
- **SC-002**: For a Job where K of N rows fail at various stages: the Job's terminal status is `completed` (NOT `failed`); `processedCount == N`; `failedCount == K`; each failed row's EvaluationResult carries `errorStatus = "failed"`, `errorStage` matching the actual stage from the finer taxonomy (per Reshape clarification), and `errorDetails`. Verifiable by automated test.
- **SC-003**: A Job with EVERY row failing reaches terminal status `completed` (NOT `failed`), with `failedCount == totalUtteranceCount`. Verifiable per US2 scenario 6.
- **SC-004**: A Cancel mid-running Job produces the exact sequence: in-flight row completes naturally; remaining Utterances get EvaluationResult stubs with `errorStatus = "cancelled"` per `009 FR-003a`; status transitions through `running → cancelling → cancelled`; password store empty for the Job. Verifiable per US3 independent test.
- **SC-005**: A simulated harness crash mid-Job, followed by restart, transitions the orphaned Job to `failed` within 5 seconds of startup with an explanatory `errorDetails`, and no Job remains in `running` or `cancelling` after the orphan pass completes. Verifiable per US4 independent test (matches parent `SC-008`).
- **SC-006**: The lone pre-row failure mode (empty password store for a Job that requires per-row passwords) results in the Job reaching terminal `failed` with `errorDetails` naming the cause; no EvaluationResult rows are created; no HTTP calls are issued. Verifiable per US6.
- **SC-007**: Two concurrent Jobs against the same registered connector + evaluator run with fully independent state (HTTP requests, password store entries, counters, statuses). Verifiable by running two Jobs simultaneously and inspecting their persisted states and instrumented mock-service incoming-request streams.
- **SC-008**: The per-row password store entry for a row is removed from the store IMMEDIATELY after the connector HTTP call returns — verifiable by instrumenting the store with a probe and asserting the absence of the entry by the time the evaluator HTTP call is dispatched.
- **SC-009**: After any Job reaches terminal status (`completed` / `failed` / `cancelled`), the in-memory password store contains zero entries keyed by that Job's `jobId`. Verifiable by probing the store at the moment of terminal transition.
- **SC-010**: The orchestrator's per-row failure-isolation behavior produces exactly one EvaluationResult per Utterance for every successfully-attempted row, regardless of whether the row succeeded or failed at any stage. Verifiable by counting EvaluationResults vs. Utterances after end-to-end runs with deliberately-induced per-stage failures.
- **SC-011**: A `running` Job's stored `status` is NEVER `CompletedWithErrors`, `Configured`, `Paused`, or any other value not in the canonical enum — verifiable by an automated test that enumerates persisted status values across many runs and asserts each is in `{draft, queued, running, cancelling, completed, failed, cancelled}`.
- **SC-012**: No HTTP call from the orchestrator EVER carries a plaintext stored credential in any logged form — verifiable by capturing the orchestrator's outbound HTTP request stream during an end-to-end test against a registration with a known-distinctive credential and grepping the captured stream's log lines for the plaintext value (zero matches expected; the value MAY appear in the actual outbound `Authorization` header per the wire protocol, but the request logging MUST NOT log that header).

## Assumptions

- This module is part of the harness defined in `specs/001-chatbot-regression-harness/spec.md`. Single-user, single-process. Concurrent multi-process orchestration is out of scope; the orchestrator assumes it is the sole orchestrator within its process.
- The orchestrator consumes (does not redefine) the interfaces and behaviors specified in:
  - Module 2 (`009`): Job, Utterance, EvaluationResult schemas; snapshot immutability; cascade delete; bulk delete; `009 FR-003a` cancellation-stub creation; transaction atomicity. The new snapshot fields named in `FR-004` are defined in `009`'s amendments for this reshape.
  - Module 4 (`007`): Connector wire protocol; generic HTTP client; auth modes; per-row timeout; bundled mock connector; at-rest credential encryption utility; serialized dispatches per job.
  - Module 6 (`006`): Standard Evaluation Contract schema; per-row validation; contract version compatibility. Note: `006`'s `errorStage` enum is extended by the 2026-05-29 Reshape clarification's finer taxonomy.
  - Module 7 (`008`): Evaluator wire protocol; generic HTTP client; closed verdict enum; standardized scores shape; declared scoring dimensions; harness-derived `harnessAnnotations`; serialized dispatches per job.
  - Module 8 (`011`): In-memory password store (the orchestrator is the canonical consumer); per-row eviction discipline; replace-on-upload semantics; the password column's required/not-required status is determined by the snapshotted connector's `expectsPerRowPassword` flag.
  - Module 9 (`003`): `draft → queued` transition on Start; enqueue signal that the orchestrator listens for.
  - Module 13 (`013`): Connector Registration CRUD (the orchestrator does not interact with `013` directly; the wizard does; the orchestrator reads from the Job's snapshot).
  - Module 14 (`014`): Evaluator Registration CRUD (analogous to `013`).
  - Module 3 (`010`): OS-derived tester identity (the orchestrator logs the identity as part of log-line prefixes per `010 FR-006`).
- The orchestrator's async / scheduling implementation (asyncio, threading, a worker pool, a separate process) is plan-level. The spec requires only the observable behaviors: async-start (`FR-001`), concurrent Jobs (`FR-022`), bounded startup orphan-reconciliation (`FR-002`).
- The maximum number of concurrent Jobs the orchestrator processes is plan-level. Parent assumption already settles this: "Concurrency limits (e.g., maximum simultaneous in-flight rows per job) are an implementation tuning concern, not a specification concern." Same applies to concurrent-Job count.
- Per-row timeouts are now part of the protocol (set per registration per `007` / `008`); the orchestrator enforces them by aborting HTTP calls locally. There is no separate orchestrator-layer timeout.
- "Plan-level" decisions about queue ordering (FIFO vs. priority), backpressure, throttling, and concurrent-job scheduling are deferred to `/speckit-plan`.
- The orchestrator's status updates (lifecycle transitions, counter updates) feed the dashboard's near-real-time row updates (per `002 FR-012`, `004 FR-015`) and the export's snapshot-at-click-time semantics (per `005 FR-003`). The orchestrator itself just writes to persistence; consumers read from there.
- The orchestrator is the SOLE source of per-row pipeline invocation. There is no debug-mode "manually invoke connector for one row" surface in v1; that would belong in some future testing-tool module. (Note: the `013` / `014` "Test connection" buttons are NOT the orchestrator — they are one-off sample-request affordances on the registry-management UI; their results are not persisted.)
- "Module 10" maps to our `012-` directory. The forward references in earlier specs to "Module 10 (TBD)" / "the orchestrator (TBD)" all resolve here.
- Historical context (superseded 2026-05-29): earlier drafts of this module described an in-process pipeline (`connect` → per-row `sendUtterance` → in-process `normalize` → in-process `evaluate` → `disconnect`) with a per-job `ConnectionHandle` and three pre-row failure modes (missing-registry / decryption-failure / `connect()`-raise). That model is replaced in full by the stateless-HTTP, two-call-per-row, single-pre-row-failure-mode design in this revision. `FR-008` / `FR-009` / `FR-010` / `FR-015` are intentionally reserved (no content) to keep cross-spec FR references stable.
