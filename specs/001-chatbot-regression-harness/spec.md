# Feature Specification: AI Chatbot Regression Test Harness

**Feature Branch**: `001-chatbot-regression-harness`

**Created**: 2026-05-28

**Last Amended**: 2026-05-29

**Status**: Draft

**Input**: User description: "A locally-installed, single-user web application that enables QA testers to systematically regression-test AI-powered chatbots. The tester uploads a CSV of test utterances (each row carrying a `testId` + `password` for an external identity), the harness fires each utterance at the target chatbot via a pluggable connector under the supplied identity, normalizes the response to a Standard Evaluation Contract, hands it to a pluggable AI-powered evaluation agent, and persists the full input → output → evaluation trace. Multiple jobs can run concurrently. Distributed as a pipx-installable Python package using embedded SQLite and a Flask UI on localhost. Multi-turn conversation support is out of scope for v1."

## Clarifications

### Session 2026-05-28

- Q: Should the tester be able to cancel a running job, and if so, what happens to in-flight rows? → A: Soft cancel. In-flight rows run to natural completion or failure; queued rows transition to "cancelled"; the job ends in a terminal "cancelled" state. Partial results are preserved.
- Q: What is the upper-bound CSV size the harness must handle without UI or persistence degradation? → A: Up to 1,000 rows per job. Larger CSVs may work but are not a design target.
- Q: How does a tester re-run only the failed rows of a completed job? → A: No first-class retry in v1. The tester filters the original CSV down to the failed rows and creates a new job. Original jobs remain immutable for traceability.
- Q: What format(s) must the results export support? → A: A single downloadable zip containing both a CSV (flat, spreadsheet-friendly, with nested fields JSON-stringified per cell) and a JSON file (lossless, nested). Both cover the same rows.
- Q: How should the harness handle transient connector failures (HTTP 429, 5xx, timeouts)? → A: No retries at the harness layer. Every connector or evaluator error is recorded as `failed` immediately with the captured cause. Individual connectors may implement internal retries at their own discretion; the harness does not.
- Q: Does a job have a "draft" state for jobs that have been created/configured but not yet started? → A: Yes. The job lifecycle is `draft` → `queued` → `running` → terminal (`completed` | `failed` | `cancelled`), with `cancelling` as the transient state on the path to `cancelled`. A `draft` job has not yet been started; testers may delete drafts but not cancel them (cancel applies only to `queued` and `running`). UI labels like "Completed with errors" are presentation only — they map to `completed` rows whose `failed`-row count is non-zero, not to a distinct state.
- Q: Beyond `draft`, are any other job statuses deletable? → A: Yes — `failed` and `cancelled` jobs MAY be deleted by the tester (`FR-001a`), to support dashboard cleanup as terminal-error jobs accumulate. `completed` jobs remain non-deletable in v1 (preserved as historical record of successful runs). Non-terminal statuses (`queued`, `running`, `cancelling`) cannot be deleted directly — the tester must cancel first.
- Q: What structure must evaluators produce for the per-row scores payload that the harness will render in the UI? → A: Each EvaluationResult MUST include an `evaluationScores` payload whose value is an ordered collection of zero or more entries, where each entry has the fields `parameter_name` (string), `score` (number or short string — the evaluator's own scale; not normalized across evaluators), and `reasoning` (string explaining that parameter's score — per-score, NOT a top-level field on EvaluationResult). The count of entries, the parameter names, and the score scales MAY differ between evaluators and between evaluator versions — the harness MUST NOT assume uniformity across evaluators. The harness owns the rendering of this payload; consumers (e.g., the Module 13 detail view) MUST treat each entry as structured data, MUST NOT inject any HTML/script the evaluator may have placed in those string fields directly into the DOM, and MUST NOT provide a sort affordance over the `evaluationScores` payload (no canonical cross-row ordering exists). *(Originally `scores` was the field name; renamed to `evaluationScores` for cross-spec consistency.)*
- Q: Originally the export was specified as "always a zip with both CSV and JSON" (`FR-015`). Module 14 wants the tester to pick the format. Which wins? → A: Module 14's selectable model wins. `FR-015` was loosened to allow the tester to pick CSV, JSON, or zip-with-both at click time. The export is also expanded to be available for any job with persisted rows (including `failed`, `cancelled`, and snapshots from `running`), not just `completed`. Partial-snapshot annotation applies when the job is non-terminal, mirroring the source-CSV download's behavior on the detail view.
- Q: Module 4 (Connector Framework) introduces an "encryption utility for the password field." Does this apply to the CSV row password (changing parent FR-010), to connector config-level secrets, or both? → A: **Config-level secrets only** — API keys, auth tokens, and service-account passwords inside the connector's own configuration form. The per-row CSV `password` rule from `FR-010` is unchanged (still in-memory only, never persisted at rest). New `FR-023a` formalizes the at-rest encryption requirement: secret-declared fields within the persisted connector and evaluator config snapshots are encrypted with a symmetric machine-local key; decrypted only when needed; never in exports, UI, or logs.
- Q: Module 3 (Tester Identity) draws a sophisticated distinction the prior rounds didn't: **tester identity** (OS-derived, no auth, for attribution + logging + UI display) vs. **test credentials** (per-utterance, opaque, in-memory only). Should the harness re-introduce a `createdBy` concept (reversing the no-creator precedent across 7 prior specs)? → A: **Yes — re-introduce attribution via OS-derived identity, while keeping zero authentication.** A new `FR-026` defines the harness's resolution of an OS-derived tester identity at startup (no login, no override). `Job.createdBy` is re-added (auto-populated; not tester-editable). The Module 12 dashboard re-adds the Created By column + filter; the Module 13 detail view re-adds Created By to its metadata panel; the Module 14 export re-adds `createdBy` to its job-metadata block; the Module 9 wizard auto-stamps `createdBy` on Job creation. Every UI surface shows a subtle "Logged in as: <user>" indicator. The per-utterance CSV `password` rule (`FR-010`) is **NOT** reversed — passwords remain in-memory only. The new attribution is purely about *which OS user* operated the harness; it is not an authentication mechanism.
- Q: Should the harness include a per-row user-feedback feature (thumbs-up/down)? → A: **No — feature removed entirely from v1.** The earlier rounds spec'd a `TesterFeedback` entity, an interactive thumbs UI in Module 13, a `feedback (if any)` mention in exports, and a `feedbackBy` field auto-populated by Module 3. All of that is dropped: `FR-014` removed, `Tester Feedback` entity removed, exports no longer carry feedback per-row, Module 13 no longer renders a User Feedback column or interactive thumbs, Module 3 no longer stamps `feedbackBy`. Rationale: the feedback feature adds non-trivial UI + persistence surface for a productivity benefit that the v1 use case doesn't require. If real-world use later shows a clear need, it can return as a v1+ feature without breaking the v1 data model (feedback would simply be added back as a new optional entity with a clean migration).

### Session 2026-05-29 (Architecture reshape)

- Q: Are connectors and evaluators in-process Python plugins (one-or-more methods, self-registration via entry points / filesystem scan / manifest, declared config JSON Schema rendered by the wizard) — OR remote HTTP services (single-endpoint wire protocol, CRUD-managed endpoint registry, endpoint + auth + timeout on the registration)? → A: **Remote HTTP services.** Each chatbot under test (and each independently-testable underlying agent) is fronted by its own connector service, hosted outside the harness. Each evaluation strategy is hosted as its own evaluator service. The harness ships a generic HTTP client per side; the wire protocols are defined in `specs/007-connector-framework` and `specs/008-evaluation-agent-framework`. CRUD over registered endpoints lives in two new modules: `specs/013-connector-registry-management` for connectors, `specs/014-evaluator-registry-management` for evaluators. The wizard's Step 3 / Step 4 become dropdowns of registered, non-archived instances; **a connector or evaluator that is not registered cannot be added to a job**. The connector service is responsible for normalizing its native chatbot response into a Standard Evaluation Contract instance before returning — so the previous in-process `normalize` step is removed. The orchestrator (`012`) issues two HTTP calls per row: one to the connector endpoint (returns a contract), one to the evaluator endpoint (returns an EvaluationResult). The four-method connector interface (`connect`/`sendUtterance`/`normalize`/`disconnect`), the in-process `evaluate(contract)` evaluator interface, the per-job `ConnectionHandle`, and the Python-entry-point / filesystem-scan self-registration mechanism are all superseded by this reshape. The CSV `password` column requirement becomes conditional on the selected connector's `expectsPerRowPassword` flag (declared on the registration in `013`). The "Test connection" affordance moves from the wizard (where it was a Step-3-only optional probe) to the registration forms in `013` / `014` (where it is an optional non-blocking button on the CRUD form). The four auth modes the harness supports out of the box are `none`, `bearer`, `api-key-header`, `basic`. Soft-delete (archival) is the default deletion semantic for registrations; hard-delete is gated when historical jobs reference the registration. Bundled mock connector and mock evaluator services ship as stub HTTP servers the harness can spin up locally for self-test.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - End-to-end regression batch under multiple identities (Priority: P1)

A QA tester wants to validate that a new chatbot release behaves correctly across a representative set of utterances and across multiple test-user identities. They install the harness, launch it, create a new test job, upload a CSV (each row: utterance + `testId` + `password` + optional metadata), pick a chatbot connector, pick an evaluation agent, supply each one's configuration, and start the job. The harness processes every row by passing the utterance to the connector authenticated as that row's identity, normalizes the chatbot's response to the Standard Evaluation Contract, runs the evaluation agent against it, and persists the full trace. When the job finishes, the tester downloads a complete results export.

**Why this priority**: This is the entire purpose of the product. Without it, no other story delivers value. It is the MVP slice.

**Independent Test**: Install the harness on a clean laptop, point it at a stub chatbot connector and a stub evaluation agent, upload a 5-row CSV with two distinct `testId`s, and verify that all 5 rows complete with persisted traces and a downloadable export containing every row.

**Acceptance Scenarios**:

1. **Given** a valid CSV with N rows and a tester who has selected a registered connector and a registered evaluation agent, **When** the tester starts the job, **Then** every row is dispatched to the connector service via HTTP under its row-specific `testId`/`password` (per `FR-006`); the connector service returns a Standard Evaluation Contract instance (per `FR-007`) which the harness forwards to the evaluator service; the input + connector response + evaluation result are persisted and linked to the job.
2. **Given** a row's `testId`/`password` fails to authenticate against the chatbot's identity system, **When** the connector service reports the failure (typically as a non-2xx response, recorded with `errorStage = "connector_response"`, or as a contract instance whose `evaluationVerdict` reflects the failure depending on the connector's internal handling), **Then** the row's EvaluationResult is persisted with the appropriate error fields and the remaining rows continue to process per the per-row failure isolation rule (`FR-016`).
3. **Given** a completed job, **When** the tester requests an export, **Then** the export contains one record per CSV row with input, normalized output, evaluation result, and any per-row error.
4. **Given** the tester closes the browser tab while a job is running, **When** the localhost server keeps running, **Then** the job continues to completion and remains reviewable on the next visit.

---

### User Story 2 - Per-row traceability review (Priority: P2)

A tester investigating a regression opens a completed (or in-progress) job and drills into individual rows to see exactly what was sent to the chatbot, what came back, how it was normalized into the Standard Evaluation Contract, what the evaluation agent decided, and (if anything went wrong) where it failed.

**Why this priority**: Traceability is what differentiates a regression harness from a one-shot script. It is required to triage failures — but the system can deliver value from P1 even before this is built.

**Independent Test**: With at least one completed job in the system, open the job's row list, open any single row, confirm the full trace (input, raw response, normalized contract, evaluation result, error if any) is visible.

**Acceptance Scenarios**:

1. **Given** a row whose status is "completed", **When** the tester opens the row's detail view, **Then** they see the original CSV input, the chatbot's raw response, the normalized Standard Evaluation Contract instance, and the evaluation agent's structured result.
2. **Given** a row whose status is "failed", **When** the tester opens it, **Then** they see which stage failed — one of the nine `errorStage` enum values defined by `012`'s 2026-05-29 Reshape clarification (`connector_transport` / `connector_response` / `connector_normalization` / `connector_auth` / `evaluator_transport` / `evaluator_response` / `evaluator_result` / `evaluator_auth` / `password_lookup`) — and the captured error detail.

---

### User Story 3 - Multiple concurrent jobs for comparative testing (Priority: P3)

A tester wants to compare two chatbot configurations (e.g., two different model temperatures, two different system prompts, or two release builds) by running them side-by-side against the same CSV. They create job A, start it, immediately create job B with a different connector configuration, and start it while A is still running. Both jobs progress independently and both results sets are independently reviewable and exportable.

**Why this priority**: Comparative testing is the headline use case for a regression harness, but it builds on top of the P1 single-job flow. Until P1 is solid, parallelism adds no value.

**Independent Test**: With P1 working, start two jobs whose CSVs and configurations differ, observe both progressing in the job list without one blocking or corrupting the other, and verify the two exports are correct and isolated.

**Acceptance Scenarios**:

1. **Given** Job A is running, **When** the tester creates and starts Job B, **Then** Job B begins processing without waiting for Job A and does not alter Job A's state.
2. **Given** two concurrent jobs, **When** both complete, **Then** each job's results contain only its own rows and its own connector/evaluator configuration snapshot.

---

### User Story 4 - Pluggable connector & evaluation agent selection at job creation (Priority: P4)

The tester picks the chatbot platform and the evaluation strategy independently when creating a job, choosing from whatever connector registrations and evaluator registrations are currently active (non-archived) in the harness's CRUD-managed registries (`013` / `014`). Per the 2026-05-29 reshape, connector and evaluator configuration (endpoint, auth, timeout, expects-per-row-password / declared scoring dimensions) lives on the registration — set up once in `013` / `014` — not on the per-job wizard. The wizard's Step 3 / Step 4 reduce to a required dropdown of active registrations; the full registration is snapshotted onto the Job at job-creation time so historical results remain interpretable even if the registration is later edited or archived.

**Why this priority**: Extensibility is core to the product's purpose, but the first release ships with at least one connector registration (the bundled mock service) and at least one evaluator registration, so the pluggability mechanism is exercised even if only one of each exists. P1 still works with a single registered pair; this story unlocks the architecture for additional pairs.

**Independent Test**: Register an additional connector endpoint via `013` and an additional evaluator endpoint via `014`, create a new job, confirm both appear in their respective dropdowns in the wizard's Step 3 / Step 4, select them, start the job, and confirm the chosen pair's full registration is snapshotted onto the job and used for execution.

**Acceptance Scenarios**:

1. **Given** at least two active connector registrations and at least two active evaluator registrations, **When** the tester opens the job creation wizard's Step 3 / Step 4, **Then** the dropdowns list every active registration.
2. **Given** the tester has selected a registered connector, **When** the wizard's Step 3 finalizes via Next, **Then** the full registration (endpoint URL, auth descriptor with encrypted credentials, timeout, expects-per-row-password flag) is snapshotted onto the Draft Job per `FR-023`. No per-job config form is rendered; configuration was already supplied at registration time in `013`.
3. **Given** a registered connector's service emits a Standard Evaluation Contract instance whose `contractVersion` is not in the bundled schema's accepted range, **When** the orchestrator dispatches a row to that connector, **Then** the per-row failure is recorded with `errorStage = "connector_normalization"` (per `006 FR-015` / `012 FR-011` step 4) and subsequent rows proceed. (The earlier wizard-time compatibility check was deprecated by the 2026-05-29 reshape; contract-version mismatches manifest at runtime now.)

---

### Edge Cases

- The uploaded CSV is missing required columns, uses a non-UTF-8 encoding, has empty rows, or has duplicate `testId`s firing different utterances.
- The chatbot connector service times out, returns a non-2xx status, returns a 2xx payload that fails harness-side validation against the Standard Evaluation Contract schema, or its stored auth credential cannot be decrypted at HTTP-call time. Each case maps to a specific `errorStage` per the 2026-05-29 reshape's finer enum: `connector_transport` (timeout / DNS / TLS / connection refused), `connector_response` (non-2xx), `connector_normalization` (2xx but invalid body), `connector_auth` (credential decryption failure).
- The evaluation agent crashes, exceeds its timeout, or returns output that does not conform to its declared output schema.
- The tester restarts the harness process while a job's status in the database is `running` or `cancelling` — the harness reconciles orphaned jobs to terminal `failed` per `012 FR-002`. Because passwords are not persisted (`FR-010`) and the in-memory password store does not survive process exit (per `011 FR-015`), rows that have not yet fired cannot resume; per `FR-010a` and `012 FR-017`, recovery requires creating a new Job and re-uploading the CSV.
- Two concurrent jobs reference the same `testId` at the same time (allowed; the harness treats this as the tester's choice, not a conflict).
- The CSV references a `testId` that no longer exists in the external identity system.
- The disk fills up or SQLite write fails mid-job.
- The user resubmits the same CSV against the same job (the harness must not silently merge — it is a new job).
- A connector service returns a contract instance whose `contractVersion` is outside the harness's bundled schema's accepted range (per the 2026-05-29 reshape this is a runtime concern, not a wizard-time gate — see `FR-020`).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST allow a tester to create and name a test job from the UI. A newly created job is in `draft` state until the tester explicitly starts it (at which point it transitions to `queued`). The tester MAY delete a `draft` job at any time before starting it.
- **FR-001a**: System MUST allow the tester to permanently delete any test job whose status is `failed` or `cancelled`. Deletion MUST cascade to all of that job's persisted Utterances and EvaluationResults (per `009 FR-010`). Jobs in any other status (`draft` excepted per `FR-001`, plus `queued`, `running`, `cancelling`, `completed`) MUST NOT be deletable. `completed` jobs are intentionally retained as the historical record of successful runs; non-terminal jobs must be cancelled to reach `cancelled` before they become deletable. Deletion MUST require explicit tester confirmation and MUST be irreversible.
- **FR-002**: System MUST accept a CSV upload whose schema requires per row at minimum: `utteranceText`, `testId`, and `password` if and only if the selected connector's `expectsPerRowPassword` flag is `true` (per `011 FR-006`/`FR-009` and `013` registration field). When the selected connector's flag is `false`, the `password` column MAY be present (preserved as metadata) or absent. Additional columns beyond the required set MUST be preserved verbatim as per-row metadata.
- **FR-003**: System MUST validate the uploaded CSV against the required schema and reject malformed uploads with row-level error messages before the job starts.
- **FR-004**: System MUST present a registry of available chatbot connectors (active, non-archived `ConnectorRegistration` records sourced from `specs/013-connector-registry-management`) and let the tester pick one per job. Per the 2026-05-29 reshape, the wizard does NOT render a per-job connector configuration form — all connector configuration (endpoint URL, auth descriptor, timeout, `expectsPerRowPassword` flag) lives on the registration. A connector that is not registered MUST NOT be selectable; the wizard MUST direct the tester to `013`'s CRUD UI to register one if the registry is empty.
- **FR-005**: System MUST present a registry of available evaluation agents (active, non-archived `EvaluationAgentRegistration` records sourced from `specs/014-evaluator-registry-management`) and let the tester pick one per job. Same pattern as `FR-004`: no per-job evaluator configuration form; all evaluator configuration lives on the registration; an unregistered evaluator MUST NOT be selectable; the wizard MUST direct the tester to `014`'s CRUD UI if the registry is empty.
- **FR-006**: System MUST forward each CSV row's `utteranceText`, `testId`, and (conditionally) `password` to the selected connector service via a single HTTP `POST` per row, per the connector wire protocol in `specs/007-connector-framework`. The `password` field MUST be included in the request body if and only if the snapshotted connector's `expectsPerRowPassword` is `true`; otherwise it MUST be omitted entirely (not sent as null, not sent as empty string).
- **FR-007**: Per the 2026-05-29 reshape, **normalization is the responsibility of the remote connector service**, not the harness. The connector service MUST return a Standard Evaluation Contract instance (the canonical, versioned JSON schema) as the body of its successful HTTP response. The harness MUST validate every received response against the bundled schema (per `006 FR-008`) and MUST treat validation failure as a per-row `connector_normalization` error. There is no in-process `normalize` step in the harness.
- **FR-008**: System MUST forward the normalized contract instance to the selected evaluator service via a single HTTP `POST` per row (per the evaluator wire protocol in `008 FR-002` and orchestrator's per-row pipeline step in `012 FR-011` step 5) and capture its structured EvaluationResult response (validated per `008 FR-005b`).
- **FR-008a**: Every EvaluationResult captured by the harness MUST include an `evaluationScores` field whose value is an ordered collection of zero or more entries. Each entry MUST be an object with the fields `parameter_name` (string), `score` (number or short string — the evaluator's own scale), and `reasoning` (string — per-parameter explanation; `reasoning` is per-score, NOT a top-level field on EvaluationResult). The count of entries, the parameter names, and the score scales are evaluator-defined and MAY vary between evaluators and between evaluator versions. The harness MUST persist the payload as structured data, MUST NOT normalize scales across evaluators, and MUST treat all string fields as data (not as HTML or executable content) when rendering them in any UI.
- **FR-009**: System MUST persist for every row: the original input row **excluding the row's `password`**, the raw chatbot response, the normalized Standard Evaluation Contract instance, the evaluation result, all relevant timestamps, the per-row status (queued / running / completed / failed / cancelled), and a link to the parent job. (Note: `draft` is a job-level state only; rows do not exist for jobs in `draft` because the CSV has not yet been bound to a started job.)
- **FR-010**: System MUST treat each row's `password` as an opaque pass-through value held **in memory only** for the duration of that row's connector call. Passwords MUST NOT be written to the local database, the exported results file, application logs, or any other persistent storage at any point in the job lifecycle.
- **FR-010a**: Because passwords are in-memory only, the system MUST NOT attempt to auto-resume rows that require credentials after a process restart. Per `FR-022`, any job whose rows still need to fire MUST transition into a tester-visible state that requires explicit re-upload of the CSV to continue, rather than silently failing or stalling.
- **FR-011**: System MUST support multiple jobs running concurrently without interference: each job's status, rows, and configuration snapshot MUST remain isolated.
- **FR-012**: System MUST surface job-level status (draft / queued / running / cancelling / completed / failed / cancelled) and per-row progress in the UI while jobs are running.
- **FR-013**: System MUST allow the tester to inspect, for any persisted row, its full input → raw output → normalized contract → evaluation result chain (or the captured error and the stage where it occurred).
- **FR-014**: *(Removed in v1 — see `Clarifications` Q on user-feedback removal. Previously specified per-row thumbs-up/thumbs-down feedback. The feature is not part of v1.)*
- **FR-015**: System MUST allow the tester to download a complete results export of any job that has at least one persisted Utterance (so: jobs in `completed`, `failed`, `cancelled`, `running`, or `cancelling` status; the `draft` and `queued` statuses have no rows and therefore no export). The harness MUST offer the tester a choice at click time of at least these three output forms: (a) a CSV file with one row per Utterance and nested structures JSON-stringified per cell, (b) a JSON file with the same rows in nested, lossless form, and (c) a zip archive bundling both (a) and (b). Whichever form is selected, the file MUST include every Utterance's input (excluding `password`), normalized output, evaluation data (`evaluationVerdict`, `evaluationScores`, etc., per `008 FR-003`), and error (if any), plus the job-level metadata snapshot (with secrets masked in the same manner as the detail view, per `specs/004-job-detail-view` → `FR-005`). The export MUST be generated on-demand at click time, always reflecting the latest persisted state including any new rows added since the last download. For jobs not yet in a terminal state, the export MUST be annotated as a partial snapshot consistent with `specs/004-job-detail-view` → `FR-006a`.
- **FR-016**: System MUST continue processing remaining rows when any individual row fails at any stage (connector error, normalization error, evaluator error). Per-row failures MUST NOT abort the whole job.
- **FR-017**: System MUST record per-row failures with the stage at which they failed and the captured error detail. The `errorStage` enum is the nine-value canonical set defined by `012`'s 2026-05-29 Reshape clarification (per `012 FR-012` / `009 FR-003`): `connector_transport`, `connector_response`, `connector_normalization`, `connector_auth`, `evaluator_transport`, `evaluator_response`, `evaluator_result`, `evaluator_auth`, `password_lookup`. (The earlier draft used a three-value `connector` / `normalization` / `evaluation` enum; that taxonomy was superseded by the reshape.)
- **FR-018**: System MUST run entirely on the tester's local machine: all persistence MUST use the embedded local database, and no functionality MUST require a remote server, shared service, or external account managed by the harness.
- **FR-019**: System MUST be installable via `pipx` and launchable with a single command that serves the UI on a localhost address.
- **FR-020**: System MUST version the Standard Evaluation Contract. Per the 2026-05-29 reshape, evaluator services no longer declare an accepted contract-version range at registration time (the registration's column set in `009 FR-001b` carries no version field) — contract-version compatibility is therefore enforced **at runtime**, not at job-creation time. When the connector service returns a contract instance whose `contractVersion` is not in the bundled schema's accepted range, the harness MUST record the per-row failure with `errorStage = "connector_normalization"` (per `006 FR-015` / `012 FR-011` step 4) and proceed to the next row. (The earlier draft required a wizard-time refusal to start; that gate was deprecated by the reshape — see `003 FR-013` reserved placeholder.)
- **FR-021**: System MUST allow new connectors and new evaluation agents to be registered without modifying any existing connector, existing evaluation agent, or the harness codebase. Per the 2026-05-29 reshape, "adding a new connector or evaluator" means (a) hosting an HTTP service that honors the wire protocol defined by `specs/007-connector-framework` (for connectors) or `specs/008-evaluation-agent-framework` (for evaluators), then (b) registering its endpoint via the CRUD UI defined by `specs/013` (connectors) or `specs/014` (evaluators). No source-tree change to the harness is required.
- **FR-022**: System MUST reconcile jobs whose status is `running` or `cancelling` at process startup (i.e., orphaned jobs after a restart) by transitioning them to a deterministic terminal state visible to the tester rather than leaving them stuck. Per `specs/012-job-execution-engine` → `FR-002`, the canonical reconciliation outcome is `failed` with an explanatory `errorDetails`. There is no `paused` lifecycle state in v1.
- **FR-023**: System MUST snapshot the full selected `ConnectorRegistration` and `EvaluationAgentRegistration` onto the job at job-creation time so historical results remain interpretable even if the underlying registry entries change later. The snapshot MUST include at minimum: the registration's `connectorId` / `evaluationAgentId`, display name (persisted as `connectorName` / `evaluationAgentName`), endpoint URL, auth descriptor (with encrypted credential ciphertext per `FR-023a`), `timeoutSeconds`, and (for connectors) `expectsPerRowPassword`, and (for evaluators) `description` + `declaredScoringDimensions`. These snapshot fields are immutable past `draft` per `009 FR-005`. Additionally, `createdBy` and `createdAt` on the Job are **immutable from the moment of Job creation** (not just past `draft`) — per `009 FR-005`'s final sentence — there is no point in the lifecycle at which they should change. Subsequent edits to the underlying registration MUST NOT alter the Job's snapshot; archival of a registration MUST NOT prevent the orchestrator from dispatching against a Job that snapshotted it; hard-deletion of a registration MUST be blocked when any historical Job references it (per `013 FR-019` / `014 FR-024`).
- **FR-023a**: Within those persisted configuration snapshots, any field that the connector or evaluation agent declared as secret (e.g., API keys, auth tokens, service-account passwords contained inside the connector's own config — NOT the per-row CSV `password` which remains in-memory only per `FR-010`) MUST be **encrypted at rest** using symmetric encryption with a machine-local key. The harness MUST decrypt these values transparently at the moment they are needed for connector authentication or evaluator invocation; decrypted values MUST NEVER appear in UI rendering (per `specs/004-job-detail-view` → `FR-005`), in exports (per `specs/005-results-export` → `FR-011`), or in application logs. Key management (key location, generation, rotation) is plan-level; the spec only requires that the key is machine-local — i.e., not in the database file, not committed to source, not portable to another machine without explicit migration.
- **FR-024**: System MUST allow the tester to cancel any job that is `queued` or `running`. On cancellation the job MUST transition to a transient `cancelling` state during which: the in-flight row (if any) MUST be allowed to run to natural completion or failure (per `012 FR-019`); rows that were never dispatched MUST receive EvaluationResult stubs with `errorStatus = "cancelled"` per `009 FR-003a`; once stub creation is complete the job MUST transition to terminal `cancelled` atomically with the stubs (per `012 FR-020`). All rows that reached `completed`, `failed`, or `cancelled` MUST remain reviewable and exportable.
- **FR-025**: System MUST NOT retry connector or evaluator calls at the orchestration layer. Every error returned by a connector or evaluator MUST be recorded as a `failed` row with the captured cause and the stage at which it occurred (per `FR-017`). Individual connectors MAY implement their own internal retry behavior, but the harness orchestrator MUST treat each per-row connector or evaluator invocation as a single shot.
- **FR-026**: System MUST resolve an OS-derived **tester identity** at process startup, before any other module reads or writes. The identity is a string drawn from the OS-user account that launched the harness; it is NOT a login credential and there is NO authentication flow. The resolved identity MUST be: (a) made available read-only to every module as application context, (b) auto-stamped onto `Job.createdBy` at Job creation, (c) rendered as a subtle "Logged in as: <user>" indicator on every UI surface (the dashboard, the detail view, the wizard), (d) included in log-line prefixes for attribution. The tester MUST NOT be able to override or edit this value from the UI. The resolution mechanism is plan-level (e.g., `os.getlogin` with `getpass.getuser` fallback and an `"unknown-user"` default); the spec requires only that the value is deterministic per process, resolved before any persistence boundary is crossed, and surfaceable for diagnostics. Test-account credentials (the per-row CSV `testId`/`password`) are unrelated to this identity and remain governed by `FR-006` / `FR-010`.
- **FR-027**: System MUST require that both a registered connector AND a registered evaluator are selected before a Job can transition from `draft` to `queued`. Per the 2026-05-29 reshape, "registered" means an active (non-archived) `ConnectorRegistration` or `EvaluationAgentRegistration` (per `013` / `014`). The wizard MUST enforce required selection at Step 3 (`003 FR-007`) and Step 4 (`003 FR-010`); when either registry is empty, the wizard MUST surface a navigation affordance to the relevant CRUD module (`003 FR-008` for connectors, `003 FR-011` for evaluators). The data layer MUST defense-in-depth refuse the `draft → queued` transition for a Job that lacks a snapshotted registration on either side or whose snapshotted id no longer resolves to an active registration.

### Key Entities *(include if feature involves data)*

- **Job** *(originally referred to as "Test Job" in some early prose)*: A single regression run. The canonical field set is defined by `009 FR-001`; this is a paraphrase of the parent-level facts. Carries: `jobName`, `description` (optional), `status` (`draft` / `queued` / `running` / `cancelling` / `completed` / `failed` / `cancelled` lowercase per `009`'s 2026-05-29 status-enum clarification), `createdBy` (OS-derived tester identity at creation time, immutable, per `FR-026`), `createdAt`, `startedAt` (null while `draft`), `completedAt`, `harnessVersion` (the harness's semantic version at job-creation time, per `009 FR-001`), `sourceCSVFilename` (the basename string only — raw file content is NOT retained per `011 FR-017`), and the full snapshotted connector + evaluator registration (per `FR-023`): `connectorId`/`connectorName`/`connectorEndpointUrl`/`connectorAuthDescriptor`/`connectorTimeoutSeconds`/`connectorExpectsPerRowPassword` and the symmetric `evaluationAgentId`/`evaluationAgentName`/`evaluatorEndpointUrl`/`evaluatorAuthDescriptor`/`evaluatorTimeoutSeconds`/`evaluatorDeclaredScoringDimensions`. Aggregate runtime counters: `totalUtteranceCount` (immutable past `draft`), `processedCount`, `failedCount`. Error sink: `errorDetails` (populated only when `status == failed`). Snapshot fields are immutable past `draft` per `009 FR-005`; `createdBy` / `createdAt` are immutable from creation.
- **Utterance**: One row from the uploaded CSV. Carries: `utteranceId` (system-generated UUID), `jobId` (FK), `utteranceText`, `rowIndex` (1-based per `009`'s 2026-05-29 Round 2 row-index clarification), `testId`, additional non-required CSV columns preserved as per-row metadata. NO persisted credential field; the per-row CSV `password` is held in an in-memory store keyed by `(jobId, utteranceId)` external to the entity (per `011 FR-015`), never persisted. (Earlier drafts called this `Test Case Row`; the canonical name is `Utterance`.)
- **EvaluationResult**: Per-row trace of one Utterance's pipeline. Carries: connector-emitted data (`rawChatbotResponse` — the raw HTTP body the connector service returned, captured for diagnosis; `normalizedContract` — the validated Standard Evaluation Contract instance per `006 FR-008`), evaluator-emitted data (`evaluationVerdict` / `evaluationScores` / `metadata` per `008 FR-003`; verdict closed enum `pass` / `fail` / `warn` per `008 FR-004`), harness-derived data (`harnessAnnotations` per `008 FR-005a`), error fields (`errorStatus` / `errorStage` / `errorDetails` per `FR-017`'s nine-value enum), and `evaluationTimestamp`. Same name as the evaluator service's HTTP response body shape per `008 FR-003` — the evaluator emits the evaluator-data subset, and the harness persists the whole row alongside the connector-emitted and harness-derived data. This entity replaces the earlier draft's separate `Connector Invocation` and `Evaluation Result` entities; see `009 FR-003` for the full shape.
- **ConnectorRegistration** *(formerly Registered Connector)*: A persisted record describing a remote connector service known to the harness. Per the 2026-05-29 reshape, registrations are managed by the CRUD module `specs/013-connector-registry-management`. Carries: harness-assigned immutable `connectorId`, tester-supplied `displayName`, optional `description`, `endpointUrl`, `authDescriptor` (mode `none`/`bearer`/`api-key-header`/`basic` per `007 FR-007` + credential ciphertext encrypted at rest per `FR-023a`), `timeoutSeconds`, `expectsPerRowPassword` boolean, `archived` flag, `createdAt`/`updatedAt`/`archivedAt` timestamps. The full record is snapshotted onto each Job at job-creation time per `FR-023`. The previous "config JSON Schema for the wizard form" concept is removed — there is no per-job config form.
- **EvaluationAgentRegistration** *(formerly Registered Evaluation Agent)*: A persisted record describing a remote evaluator service known to the harness. Per the 2026-05-29 reshape, registrations are managed by the CRUD module `specs/014-evaluator-registry-management`. Carries: harness-assigned immutable `evaluationAgentId`, tester-supplied `displayName`, required `description`, `endpointUrl`, `authDescriptor` (same shape as connector, encrypted per `FR-023a`), `timeoutSeconds`, ordered `declaredScoringDimensions` list (MAY be empty), `archived` flag, `createdAt`/`updatedAt`/`archivedAt` timestamps. Snapshotted onto each Job at job-creation time. The previous "config JSON Schema" / "declared contract version" fields are removed — contract version compatibility becomes a runtime concern, not a registration-time declaration.
- **Standard Evaluation Contract Schema** *(bundled artifact, NOT a persisted entity)*: The canonical, versioned JSON schema that defines the integration seam between connector services and evaluator services. Bundled with the harness as a single latest version per `006 FR-015`; not stored per job, not declared by registrations. Listed here because every other module references it (`006`, `007`, `008`, `009`, `012`); not a row in the database.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A tester starting from a clean machine can install the harness, launch it, and start their first job in under 10 minutes.
- **SC-002**: A 100-row regression job runs to completion without manual intervention, with every row reaching a terminal per-row status (completed or failed) and never stuck mid-stage.
- **SC-003**: For any row in any completed job, the tester can locate the original input, the chatbot's response, and the evaluation result in under 30 seconds starting from the job dashboard.
- **SC-004**: A tester can run three jobs concurrently with no observable interference — each job's results, statuses, and configuration snapshots remain correct and isolated.
- **SC-005**: A completed job's exported results contain 100% of the rows from the input CSV; no rows are silently dropped.
- **SC-006**: Adding a new chatbot platform or a new evaluation strategy requires zero changes to any existing connector, any existing evaluation agent, or the core orchestrator.
- **SC-007**: Per-row credentials from the CSV are reachable by the selected connector for the duration of that row's call only. They never appear in any persisted form — not in the local database, not in any exported results file, and not in application logs — verifiable by inspecting those artifacts after any completed or failed job.
- **SC-008**: When the harness process is restarted, no job remains in `running` or `cancelling` state — every previously-orphaned job appears in a deterministic, tester-visible terminal state (`failed` per `FR-022`'s canonical reconciliation) within 5 seconds of startup.
- **SC-009**: When a connector service returns a contract instance whose `contractVersion` is not in the bundled schema's accepted range, the affected row's persisted EvaluationResult carries `errorStage = "connector_normalization"` with `errorDetails` naming the version mismatch; subsequent rows proceed. (Per the 2026-05-29 reshape, contract-version compatibility is a runtime concern; the prior wizard-time refusal-to-start has been deprecated to runtime — see `FR-020`.)
- **SC-010**: A 1,000-row job runs to completion on a typical tester laptop with the job dashboard, row list, and row detail view remaining usable (no full-page hang) throughout the run.
- **SC-011**: When a CSV upload exceeds 1,000 rows, the tester sees a clear, actionable warning at upload time stating that the job is above the supported design target; the tester may proceed at their discretion, but the harness makes no responsiveness or completion-time guarantees beyond 1,000 rows.

## Assumptions

- The tester has Python and `pipx` available locally. Bootstrapping Python itself is out of scope.
- The tester has network reachability from their laptop to the target chatbot endpoint and to whatever identity system the connector authenticates against.
- Test accounts referenced by `testId`/`password` in the CSV are pre-existing in an external identity system; the harness does not provision, rotate, or validate them out-of-band.
- The CSV's column schema is documented and stable: required columns are `utteranceText` and `testId` always, plus `password` when the selected connector's `expectsPerRowPassword` is `true` (per `FR-002` and `011 FR-006`). Additional columns are preserved as per-row metadata but not interpreted.
- Evaluation is non-deterministic: re-running the same row may yield a different evaluation result, and that variability is acceptable and expected by users.
- Multi-turn / context-carrying conversations across multiple CSV rows are out of scope for v1. Each row is an independent single-turn invocation.
- First-class retry of failed rows is out of scope for v1. Completed jobs are immutable; a tester who wants to re-run failed rows does so by filtering their CSV and creating a new (independent) job. There is no parent-child job linkage in v1.
- The harness is a single-user tool. Because it runs on localhost on the tester's laptop, no authentication or authorization layer is needed inside the harness itself.
- Concurrency limits (e.g., maximum simultaneous in-flight rows per job) are an implementation tuning concern, not a specification concern.
- The design target is jobs of up to 1,000 utterances. CSVs above that may still process but are out of scope for performance and UI-responsiveness guarantees.
- The export file format and the specific Standard Evaluation Contract schema content are implementation-plan decisions; the spec only requires that they be canonical, versioned, and complete.
- The fourteen internal modules referenced in the input ("foundational layers, integration layers, orchestration, UI/experience") are architectural detail and belong in the implementation plan rather than the spec.
- Module map (post-2026-05-29 reshape): the harness is composed of 14 module specs — `001` parent (this spec), `002` dashboard, `003` job-creation wizard, `004` job detail view, `005` results export, `006` evaluation contract, `007` connector framework (wire protocol + generic HTTP client + bundled mock), `008` evaluation agent framework (wire protocol + generic HTTP client + bundled mock), `009` data model & persistence, `010` tester identity, `011` CSV upload & validation, `012` job execution engine (orchestrator), `013` connector registry management (CRUD for connector endpoints), `014` evaluator registry management (CRUD for evaluator endpoints).
