# Feature Specification: Standard Evaluation Contract

**Feature Branch**: `006-evaluation-contract`

**Created**: 2026-05-28

**Last Amended**: 2026-06-01

**Status**: Draft

**Input**: User description: "Define a versioned canonical JSON schema that serves as the single integration contract between chatbot connectors (producers) and evaluation agents (consumers). Required fields: `utteranceId`, `utteranceText`, `testId`, `conversationContext` (reserved for future multi-turn, defaults to null), `chatbotResponse` (containing `rawPayload`, `normalizedText`, `agentChain`, `metadata`), `connectorId`, and `timestamp` (ISO-8601). Every instance carries a `contractVersion`. The schema is extensible — additional optional fields can be added without breaking existing consumers. Validation utility takes any JSON object and returns conformance + detailed errors."

> **Parent context**: This module formally defines the **Standard Evaluation Contract** abstractly referenced by `specs/001-chatbot-regression-harness/spec.md` (`FR-007`, `FR-008`, `FR-020`, the `Standard Evaluation Contract Schema` Key Entity). This spec scopes itself to the **connector service → harness → evaluator service** handoff (the wire format the harness receives from connector services per `007 FR-003` and forwards to evaluator services per `008 FR-002`). The reverse handoff (evaluator → harness, the `EvaluationResult` shape) is defined by `008 FR-003` (evaluator emission) and persisted per `009 FR-003`; it is **out of scope here**. Per the 2026-05-29 architecture reshape, contract instances are HTTP message bodies, not in-process objects; they are produced by remote connector services (not by an in-process `normalize()` step in the harness) and consumed by remote evaluator services. The harness's role is to (a) validate the contract instance received from the connector service against the bundled schema (per `FR-008` / `FR-015`) and (b) forward the validated instance to the evaluator service. Parent-spec premises apply: single-user, no auth. The contract instance itself carries no `createdBy` field (it's per-row payload, not Job-level metadata); parent `FR-026`'s OS-derived `Job.createdBy` lives elsewhere. The user's input mention of "a JSON Schema definition file and a validation utility function" is treated as **plan-level deliverables** — this spec defines the contract's shape and the validation *behavior*; the file format, language binding, and function signature are decided during `/speckit-plan`.

## Clarifications

### Session 2026-05-28

- Q: How does contract versioning work? → A: **Additive-only never bumps; structural changes bump.** Adding a NEW optional field to the contract MUST NOT change `contractVersion` (consumers built for prior version values continue to ignore the new field). Removing a field, renaming a field, changing a field's type, changing a field's semantic meaning, or making an existing optional field required IS a breaking change and MUST cause a new `contractVersion` value to be issued. Per parent `FR-020` (rewritten in the 2026-05-29 reshape), compatibility is enforced at **runtime** against the bundled schema's accepted range (per `FR-015` of this spec); the previous "evaluation agents declare which `contractVersion` values they accept" model was dropped when evaluator registrations stopped carrying any contract-version field (per `014` / `009 FR-001b`).
- Q: What is the uniqueness scope for `utteranceId`? → A: **Globally unique** within the harness installation (e.g., UUID v4 or equivalent). Generated by the harness when a Utterance is persisted (not by the connector). The id is meaningful even outside of any single job — a downstream consumer concatenating exports from multiple jobs MUST NOT see collisions on `utteranceId` alone. (This is independent of `testId`, which is the CSV-supplied identity for authentication and MAY appear on rows of multiple different jobs.)

### Session 2026-05-28 (Round 2)

- Q: What format is the `contractVersion` value? → A: **Integer-only string** (`"1"`, `"2"`, `"3"`, …). The additive-only-never-bumps rule (`FR-006`) means there's no concept of "minor" or "patch" — every bump is by definition a breaking change. Integer-only matches that exactly. The harness's bundled schema (`FR-015`) is the sole authority for what `contractVersion` values are accepted; runtime validation uses numeric comparison against the bundled version. No range syntax, no comparator semantics, no semver tooling. The value is stringified for transport (the JSON field is a string, not a numeric type) to avoid edge cases with JSON number-precision and to keep the door open for a future change to a non-numeric scheme without re-typing every existing instance.
- Q: Does the harness bundle one schema (the latest) or multiple historical schemas at runtime? → A: **Single bundled schema = always the latest.** Historical schema artifacts are not retained at runtime. The additive-only-never-bumps rule (`FR-006`) guarantees a V_N instance still structurally conforms under V_N+1's schema, so older `contractVersion` values are accepted by validation when the instance is structurally conformant to the bundled latest. Instances with `contractVersion` values *greater* than the bundled schema's version are rejected at runtime (the connector service is ahead of the harness; that's a configuration mismatch — per the 2026-05-29 reshape there is no wizard-time check, so this rejection is the sole gate and manifests as `errorStage = "connector_normalization"` per `FR-009`). Comparison of `contractVersion` values across "less than / equal / greater than" MUST treat them as integers (numeric comparison, not lexicographic), even though they're transported as strings.

### Session 2026-05-29 (Reshape)

- Q: The 2026-05-29 architecture reshape moved connectors and evaluators to remote HTTP services managed by CRUD modules (`013`/`014`), refined the harness's `errorStage` enum from three values to nine, and deprecated the wizard-time contract-version compatibility check. What changes for the contract? → A: **Three semantic adjustments, no schema-content changes:**
  1. The contract instance is now the **HTTP response body returned by the connector service** (per `007 FR-003`) and the **HTTP request body sent to the evaluator service** (per `008 FR-002`). It is also persisted as `EvaluationResult.normalizedContract` per `009 FR-003`. There is no in-process `normalize()` step in the harness — the connector service produces the contract instance internally before returning it. The contract's role as wire format does not change its shape (the required and optional fields enumerated in `FR-002` / `FR-003` are unchanged), only its delivery mechanism.
  2. The validation-failure stage in `FR-009` is canonicalized to **`connector_normalization`** (one of the nine `errorStage` enum values per `012`'s 2026-05-29 Reshape clarification / `009 FR-003`). The earlier draft used the unprefixed `"normalization"` from the three-value taxonomy; that value is superseded.
  3. The wizard-time compatibility check (formerly `FR-012` of this spec + parent `FR-020`) is **deprecated**: evaluator registrations carry no contract-version field (per `014` / `009 FR-001b`), so there is no per-evaluator declaration to check against. Contract-version compatibility is now enforced **strictly at runtime** by `FR-015`'s bundled-schema rules; mismatches are recorded as `errorStage = "connector_normalization"` per `FR-009`. `FR-012` is correspondingly marked as **reserved** (no current content); subsequent specs reference runtime validation only.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A connector produces a contract instance the evaluator can consume (Priority: P1)

A chatbot connector service (e.g., the MS Copilot Studio connector or the Semantic Kernel connector) receives a per-row HTTP request from the harness (`utteranceText` + `testId` + `password?` per `007 FR-002`), calls its target chatbot, and constructs an instance of the Standard Evaluation Contract from the raw response. The connector service returns the contract instance as its HTTP response body (per `007 FR-003`). The harness validates the instance against the bundled schema (per `FR-008` / `FR-015`) and, on success, forwards the validated instance as the HTTP request body to the selected evaluator service (per `008 FR-002`). The evaluator service reads the well-known fields, evaluates, and emits its EvaluationResult. This is the integration seam working as designed.

**Why this priority**: Without this story, no end-to-end flow works. The contract IS the integration. This is the MVP slice of Module "Standard Evaluation Contract."

**Independent Test**: With a stub connector that produces a hand-rolled, schema-conformant contract instance and a stub evaluator that reads only the required fields, run a one-row job and verify (a) the harness accepts the instance, (b) the evaluator receives the expected `utteranceText`, `chatbotResponse.normalizedText`, and `testId` values, (c) the evaluator's result is captured by the harness without contract-related errors.

**Acceptance Scenarios**:

1. **Given** a connector service that produces a contract instance containing every required field with valid types and a `contractVersion` value within the bundled schema's accepted range (per `FR-015`), **When** the harness validates the instance, **Then** validation passes and the instance is forwarded to the evaluator service unchanged.
2. **Given** the same scenario, **When** the evaluator consumes the instance, **Then** the values for `utteranceText`, `testId`, `chatbotResponse.normalizedText`, and `chatbotResponse.rawPayload` are byte-equal to what the connector emitted.

---

### User Story 2 - Reject a non-conforming contract instance at the harness boundary (Priority: P1)

A connector service emits a malformed contract instance — missing a required field, wrong type for a field, or `contractVersion` outside the bundled schema's accepted range. The harness catches this at validation time, refuses to forward it to the evaluator service, and records the row as failed with `errorStage = "connector_normalization"` and human-readable detail of which field is wrong. The evaluator service never receives the malformed instance.

**Why this priority**: Validation is what makes the contract a contract. Without it, a buggy connector silently corrupts an evaluation pipeline. Equal-priority with US1.

**Independent Test**: With a stub connector service that emits in turn (a) an instance missing `utteranceId`, (b) an instance whose `timestamp` is not ISO-8601, (c) an instance whose `chatbotResponse.normalizedText` is a number instead of a string, run a one-row job for each. Verify in every case that the row is recorded as failed with `errorStage = "connector_normalization"` per the nine-value enum (per `012 FR-012` / `009 FR-003`), that the failure reason names the specific field and what was wrong with it, and that the evaluator service is never called.

**Acceptance Scenarios**:

1. **Given** a contract instance missing one of the required fields, **When** the harness validates it, **Then** validation fails, the failure detail names the missing field, and the row is recorded as failed without invoking the evaluator.
2. **Given** a contract instance whose field types do not match the schema (e.g., `timestamp` is a Unix integer instead of an ISO-8601 string), **When** the harness validates it, **Then** validation fails, the failure detail names the offending field, expected type, and observed type, and the evaluator is never invoked.
3. **Given** a contract instance whose `contractVersion` is greater than the harness's bundled schema version (per `FR-015`), **When** the harness validates the instance, **Then** validation fails with a contract-version-mismatch detail naming both the instance's version and the bundled version, the row is recorded as failed with `errorStage = "connector_normalization"`, and the evaluator service is never called. Subsequent rows of the same job MAY also fail the same way if the connector continues to emit out-of-range versions; each row is recorded independently per the per-row failure isolation rule (`001 FR-016`).

---

### User Story 3 - Add a new optional field to the contract without breaking existing evaluators (Priority: P2)

The harness team (or a connector author) adds a new optional field to the schema — for example, a `chatbotResponse.metadata.toolCallCount` field that a few advanced connectors will emit. The contract's `contractVersion` does NOT change. Existing evaluators that don't know about the new field continue to read the fields they do know about and ignore the rest. Newer evaluators that DO know about the field can take advantage of it when present.

**Why this priority**: This is the extensibility property the user's input explicitly calls out. Without it, every new field requires lock-step upgrades of every evaluator. Less critical than US1/US2 because the system delivers value even before the first additive change is needed.

**Independent Test**: Take a working evaluator built against the contract as published. Have a connector emit a contract instance with one extra field the evaluator does not know about (e.g., `chatbotResponse.metadata.someNewField`). Verify (a) the harness still validates the instance as conforming, (b) the evaluator processes it normally, ignoring the unknown field, (c) the new field is preserved through to persistence and shows up in the exported `rawPayload` / `metadata` blocks.

**Acceptance Scenarios**:

1. **Given** a contract instance containing the schema's required fields plus one or more additional fields not named by the schema, **When** the harness validates the instance, **Then** validation passes (the schema allows additional properties; unknown fields are not a violation).
2. **Given** an evaluation agent that reads only a subset of the schema's named fields, **When** the harness hands it an instance with extra unknown fields, **Then** the evaluator's behavior is unchanged from when it was given an instance with no extras.

---

### User Story 4 - Reject changes that would silently break consumers (Priority: P3)

A contributor proposes a schema change that removes a field, renames a field, changes a field's type, or makes an optional field required. The change cannot land at the same `contractVersion` value — the contract's versioning policy forces a new `contractVersion`. The harness boundary then becomes the safety net: the bundled schema in a given harness release defines the accepted-version range (per `FR-015`), and any contract instance whose `contractVersion` is outside that range fails at runtime with `errorStage = "connector_normalization"`. Connector services that have shipped against the previous version continue to work against older harness releases; testers upgrading the harness pick up the new accepted-version range automatically.

**Why this priority**: The versioning rule is what makes US3 safe. Without it, the "additive-only never bumps" promise is uncheckable. Lower priority than US3 because it's about process discipline, not runtime behavior.

**Independent Test**: Compare two versions of the schema where one removes or renames a field. Verify that any tooling enforcing the versioning policy flags the change as breaking and requires a new `contractVersion` value.

**Acceptance Scenarios**:

1. **Given** a proposed schema change that removes a required or optional field, **When** the change is checked against the previous schema, **Then** the change is flagged as breaking and MUST be accompanied by a new `contractVersion` value.
2. **Given** a proposed schema change that changes a field's type or makes an optional field required, **When** the change is checked, **Then** it is flagged as breaking and requires a new `contractVersion`.

---

### Edge Cases

- A connector emits a contract instance where `chatbotResponse.agentChain` is an empty array — this MUST be valid (non-agentic connectors have no agents to enumerate). An empty array is semantically distinct from a missing field.
- A connector emits a contract instance where `chatbotResponse.metadata` is `{}` (empty object) — valid; metadata is free-form connector-specific data and zero entries is allowed.
- A connector emits a contract instance where `conversationContext` is `null` — valid; this is the expected v1 value because multi-turn is out of scope (parent assumption).
- A connector emits a contract instance where `conversationContext` is a non-null object — valid but ignored by v1 evaluators; reserved for future multi-turn support without breaking the contract version.
- A connector service emits a contract instance whose `contractVersion` is greater than the bundled schema's version — the harness MUST treat this as a hard validation failure with an actionable message naming both the instance's `contractVersion` and the bundled version; the row is recorded as failed with `errorStage = "connector_normalization"` per `FR-009`.
- Two different connectors emit `chatbotResponse.metadata` keys with the same name but different semantics (e.g., one's `latency` is millisecond, the other's is seconds) — the schema does NOT police semantics of metadata values. This is acceptable; metadata is connector-specific. Downstream consumers (UI rendering, exports) treat metadata as opaque structured data.
- A connector emits a string `timestamp` that is not valid ISO-8601 — validation fails; the row is recorded as failed.
- A connector emits `utteranceId` as a non-string value (number, null) — validation fails; the row is recorded as failed.
- The harness ships a new bundled schema with an additional optional field; an older connector service continues to emit instances without that field — valid; the new field is optional and absence is allowed.
- The harness ships a new bundled schema with an additional optional field; a newer connector service emits the field with a value; an evaluator service built before the addition consumes the instance — valid; the evaluator simply does not read the new field.
- A connector service emits `chatbotResponse.normalizedText` containing characters that are valid Unicode but would need escaping in other formats (newlines, quotes, embedded markup) — valid; the field is a JSON string and JSON's own escaping rules apply. Downstream consumers (`004` detail view, `005` export) are responsible for safe rendering.
- A consumer calls the validation utility on an object that is not a contract instance at all (e.g., a chatbot's raw response payload) — the utility MUST return non-conformance with a clear detail (e.g., missing top-level required fields), not crash.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST publish a single canonical schema definition for the **Standard Evaluation Contract** that names and types every required field, every optional field, and the rules for additional (extension) fields. The schema definition MUST be a versioned artifact; its on-disk format (e.g., JSON Schema, OpenAPI fragment, equivalent) is a plan-level decision.
- **FR-002**: Every contract instance MUST carry the following required top-level fields:
  - `contractVersion` — string identifying the contract version this instance conforms to. Format is an **integer expressed as a string** (`"1"`, `"2"`, `"3"`, …). Each value is incremented by exactly one when a structural (breaking) change is published (per `FR-007`). There are no minor or patch components. Comparison against the bundled schema's accepted range (per `FR-015`) uses numeric comparison (per `FR-016`).
  - `utteranceId` — string, globally unique within the harness installation (UUID v4 or equivalent), generated by the harness when the Utterance is persisted.
  - `utteranceText` — string, the original user input from the CSV row (the value of the row's `utteranceText` column).
  - `testId` — string, the CSV-supplied identity associated with the row.
  - `conversationContext` — object OR null. In v1 this MUST be `null` (multi-turn is out of scope per parent spec); a non-null object is permitted forward-compat but evaluators MUST NOT depend on its shape until a future contract version pins it.
  - `chatbotResponse` — object, see `FR-003`.
  - `connectorId` — string, the identity of the connector service that produced this instance (matching the `ConnectorRegistration.connectorId` per `009 FR-001a` of the registration the Job snapshotted at creation time).
  - `timestamp` — string, ISO-8601 (RFC 3339-compatible) datetime indicating when the harness constructed this contract instance (after receiving the chatbot's response).
- **FR-003**: The `chatbotResponse` object MUST contain the following required sub-fields:
  - `rawPayload` — opaque object (or array, or string — connector's choice of shape) carrying the raw chatbot response exactly as the connector received it before normalization. The schema MUST NOT constrain this field's internal shape.
  - `normalizedText` — string, the connector's best plain-text rendering of what the chatbot said. This is what the evaluator typically reads first. Empty string is allowed (e.g., a chatbot that returned only structured data with no human-facing text).
  - `agentChain` — array of strings. Ordered list of agent identifiers invoked during response generation. Empty array `[]` is valid (non-agentic connectors); the field MUST be present.
  - `metadata` — object, free-form, connector-specific. Common examples: `latency`, `tokenCount`, `modelVersion`. The schema MUST NOT name specific metadata keys; each connector documents its own metadata keys. Empty object `{}` is valid; the field MUST be present.
- **FR-004**: The contract MUST permit `password` in NO field whatsoever. Per parent `FR-010`, passwords are in-memory only and never persisted; the contract is the connector → evaluator handoff and the evaluator has no need for credentials. Validation MUST treat any `password` key as a schema violation regardless of which level it appears at.
- **FR-005**: The contract MUST be extensible with additional optional fields. Specifically, schema validation MUST treat unknown fields (top-level or nested) as conforming, not as violations. Consumers (evaluators) MUST NOT fail when they receive a contract instance with unknown fields they do not read.
- **FR-006**: Adding a new optional field to the schema MUST NOT change `contractVersion`. Existing producers (connectors that don't emit the field) and existing consumers (evaluators that don't read the field) MUST continue to function identically.
- **FR-007**: The following schema changes ARE breaking and MUST cause a new `contractVersion` value to be issued:
  - Removing a field (required or optional).
  - Renaming a field.
  - Changing a field's type.
  - Changing a field's semantic meaning while keeping its name and type.
  - Making an existing optional field required.
  - Changing the rules of `additionalProperties` (e.g., flipping from allowed to forbidden).
- **FR-008**: The harness MUST validate every contract instance against the published schema at the boundary between connector output and evaluator input, BEFORE handing the instance to the evaluator. Validation MUST run for every per-row contract instance, not just sampled rows.
- **FR-009**: If validation fails, the harness MUST:
  - NOT forward the instance to the evaluator service for this row.
  - Record the row as failed (per parent `FR-016`, `FR-017`).
  - Capture as the failure detail (a) the specific failing field path (e.g., `chatbotResponse.normalizedText`), (b) the violation kind (missing, wrong type, value out of range, etc.), (c) the expected and observed values where applicable, and (d) the `contractVersion` of the instance.
  - The failure stage label MUST be **`connector_normalization`** — one of the nine canonical `errorStage` enum values per `012`'s 2026-05-29 Reshape clarification (canonicalized in `012 FR-012` and `009 FR-003`; mapped from the connector wire protocol per `007 FR-006`). The earlier draft used the unprefixed `"normalization"` from the deprecated three-value taxonomy; that value is superseded.
  - Continue processing remaining rows (per parent `FR-016` — per-row failures don't abort the job).
- **FR-010**: The harness MUST expose a validation behavior accessible to connector and evaluator authors during development: given any JSON object, it MUST return (a) a boolean indicating whether the object conforms to the contract, and (b) if non-conformant, a structured list of per-field violations with the same detail required by `FR-009`. The concrete shape of this surface (function, CLI, REST endpoint, etc.) is plan-level; the spec requires only that the validation behavior is reachable for non-runtime authoring use.
- **FR-011**: Validation MUST be deterministic: the same input JSON object MUST produce the same conformance result and the same error list across runs. No randomness, no time-dependent rules.
- **FR-012**: *(Reserved — formerly required a wizard-time refusal-to-start when the selected connector's emitted contract version was not in the selected evaluator's declared accepted-version set. Deprecated by the 2026-05-29 reshape: evaluator registrations no longer carry a contract-version field (per `014` / `009 FR-001b`), so there is no per-evaluator declaration to check against. Contract-version compatibility is now enforced strictly at runtime per `FR-015` and surfaces as `errorStage = "connector_normalization"` per `FR-009`. The FR number is preserved for stable cross-spec references; current content: no requirement.)*
- **FR-013**: The schema MUST treat ISO-8601 / RFC 3339 datetime strings as the canonical timestamp form. Non-conformant timestamp formats (Unix epoch integer, locale-specific strings) MUST fail validation.
- **FR-014**: The schema MUST publish a meaningful, human-readable description of every field — what it means, what produces it, what consumes it, valid values, examples. The description's form (schema-embedded annotations, separate prose document, both) is plan-level.
- **FR-015**: The harness MUST bundle exactly one schema artifact at runtime — the latest published `contractVersion`. Historical schema artifacts MUST NOT be retained at runtime. Runtime validation behavior MUST be:
  - An instance whose `contractVersion`, interpreted numerically, is **equal to** the bundled schema's version MUST be validated against the bundled schema.
  - An instance whose `contractVersion`, interpreted numerically, is **less than** the bundled schema's version MUST also be validated against the bundled schema. Per `FR-006`'s additive-only-never-bumps rule, this validation passes when the instance is structurally conformant; no version-specific schema lookup is needed.
  - An instance whose `contractVersion`, interpreted numerically, is **greater than** the bundled schema's version MUST be rejected as a validation failure. The failure detail MUST name both the bundled version and the instance's declared version, and MUST suggest "update the harness" as the likely remediation. Per parent `FR-020` (rewritten in the 2026-05-29 reshape), this is the **primary** mechanism for catching contract-version mismatches — there is no wizard-time gate (the prior "connector-registration version check" was deprecated when evaluator registrations stopped carrying a contract-version field).
- **FR-016**: All numeric comparisons of `contractVersion` values MUST interpret the stringified value as an integer. Lexicographic comparison MUST NOT be used (it would order `"10"` before `"2"`).

### Key Entities *(include if feature involves data)*

- **Standard Evaluation Contract** (the schema): The canonical definition of the connector → evaluator instance shape. Lives as a versioned artifact. Carries: a `contractVersion` value, the set of named required fields with types, the set of named optional fields with types, the extensibility policy (additional fields allowed), and per-field human-readable descriptions.
- **Contract Instance**: A single JSON object emitted by a connector and consumed by an evaluator, conforming to a specific `contractVersion` of the schema. One contract instance corresponds to one Utterance's chatbot call. Carries the fields enumerated in `FR-002` and `FR-003`.
- **Validation Result**: The output of running validation against a candidate contract instance. Carries: a boolean `valid`, and (when invalid) a list of per-violation records each carrying the field path, the violation kind, expected and observed values where applicable, and the candidate's `contractVersion` value.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A hand-rolled, schema-conformant contract instance passes the harness's validation and reaches the evaluator unchanged — verifiable by a round-trip test that hashes the input and compares to the value the evaluator sees.
- **SC-002**: A contract instance with a missing required field is rejected; the resulting per-row failure carries a detail string that names the specific missing field — verifiable by inspecting the row's persisted error detail after the run.
- **SC-003**: A contract instance with a type-incorrect field is rejected; the per-row failure detail names the offending field, expected type, and observed type — verifiable by inspection.
- **SC-004**: A contract instance whose `contractVersion` is greater than the bundled schema's version is rejected at runtime; the failure detail names both the instance's `contractVersion` and the bundled schema's version, and the row's persisted `errorStage` is `connector_normalization` — verifiable by inspection.
- **SC-005**: A contract instance with one or more unknown extension fields validates as conforming; the evaluator processes it without error; the unknown fields are preserved through to row persistence — verifiable by exporting the row and finding the unknown fields in the `rawPayload` or `metadata` blocks.
- **SC-006**: Adding a new optional field to the schema does NOT cause any previously-conformant instance to become non-conformant, and does NOT change `contractVersion` — verifiable by a schema-diff tool or equivalent process check.
- **SC-007**: Removing or renaming any field, changing any field's type, or making any optional field required produces a new `contractVersion` value — verifiable by enforcing the policy during schema review (CI check, codified review checklist, or equivalent).
- **SC-008**: For any candidate JSON object, the validation behavior is reachable outside of a running job (during connector or evaluator development) and returns a structured per-violation list when the object does not conform — verifiable by a unit test calling validation directly on hand-rolled inputs.
- **SC-009**: Validation is deterministic — running it twice on the same input produces the same `valid` flag and the same violation list (order, content, count) — verifiable by repeated calls.
- **SC-010**: 100% of connector-service → evaluator-service forwards in a running job pass through harness-side validation (per `FR-008` and the per-row pipeline in `012 FR-011` step 4); there is no path by which a non-conformant instance reaches the evaluator service — verifiable by code review or by injecting an invalid instance through every code path that handles a connector HTTP response and observing rejection in every case.

## Assumptions

- This module is part of the harness defined in `specs/001-chatbot-regression-harness/spec.md`. Single-user, no auth. The contract instance itself carries no `createdBy` field (it is a per-row payload from connector to evaluator, not Job-level metadata). Parent `FR-026` adds OS-derived `Job.createdBy` (and `Job.connectorName` / `Job.evaluationAgentName`) at the Job level, but those fields are not part of this per-row contract.
- This spec defines the **connector → evaluator** contract only. The **evaluator → harness** output side (the `EvaluationResult` shape) is defined by `008 FR-003` (agent-emitted subset) and persisted per `009 FR-003` (full row). A symmetric "Standard Evaluation Result Contract" is out of scope for this spec.
- The actual on-disk format of the schema definition (JSON Schema draft 2020-12, OpenAPI 3.x fragment, ProtoBuf, etc.) is a plan-level decision. The spec requires only that the schema is a versioned artifact with the named fields and the named policies.
- The validation behavior's concrete delivery (a Python function, a CLI utility, a REST endpoint, all three) is a plan-level decision. The spec requires only that validation runs at the harness's connector→evaluator boundary and is reachable for authoring use.
- "Globally unique" for `utteranceId` is interpreted as unique within the harness installation. The harness has no concept of a shared / multi-installation namespace.
- The `chatbotResponse.rawPayload` field is intentionally schema-unconstrained — connectors emit whatever the chatbot natively returns. The contract owns only the path TO it (`chatbotResponse.rawPayload`), not the shape AT it.
- `chatbotResponse.metadata` keys are connector-specific. There is no standardized vocabulary for metadata keys in v1. If a future contract version wants to standardize specific keys (e.g., `latency_ms`), that's a breaking change requiring a new `contractVersion`.
- The `conversationContext` field is present in v1 but always `null`, as a forward-compat placeholder for multi-turn support. Connectors and evaluators MUST emit / handle `null` for this field in v1.
- The `contractVersion` format is fixed: monotonically-incrementing integer expressed as a string (`"1"`, `"2"`, …). Comparison is exact string equality. Rationale: the additive-only-never-bumps rule (`FR-006`) means every bump is breaking, so minor/patch components serve no purpose. See `FR-002` and `Clarifications` Q (Round 2).
